### 1.2 根因分层

| 层 | 根因 | 证据 |
|----|------|------|
| 表层 | Reviewer 子 agent 空返回，审核报告拿不到 | 08-13 连续两次；08-06 先例 `No active team found` |
| 中层 | 自动化 prompt 的异常表只有"超时 10 分钟跳过"，没有"空返回/非 JSON"口径 | 数据库 prompt 阶段2 原文可查 |
| 深层 | **spawn 的 Agent 工具是前台阻塞调用。子 agent 内部异常时工具不返回，主代理没有时钟概念去执行"10 分钟后跳过"，只能干等**，最终平台 90 分钟超时 | 13:57 那次 90 分钟整点超时即为铁证 |

### 1.3 关键洞察：为什么"纸面规则"防不住卡死

- 检查发现 **SKILL.md 的异常表（第 210 到 217 行）其实早就写了**"reviewer 返回空结果 → 重试 1 次，仍为空则跳过审校"。
- 但这条规则**防不住**，因为：主代理执行到 spawn 那一步时，`Agent` 工具调用是**阻塞等待**的。工具不返回，主代理就走不到"判空 → 重试 → 跳过"的分支——它根本没有机会执行这条规则。
- 结论：**只要依赖"spawn + 回传"这条链路，无论写多少异常规则都防不住阻塞**。唯一可靠的做法是**不依赖该链路**（同步执行），这正是本方案的核心。

## 3. 联网调研：业界子代理可靠性实践（备选方案来源）

| 来源 | 模式 | 要点 | 对本项目的映射 |
|------|------|------|----------------|
| CopilotKit Strands（子代理文档） | **空返回占位符 + 哨兵值** | 子代理成功但无内容 → 用占位符 `(sub-agent returned no content)` 替代，归类为"completed"，不抛异常；失败用 `__SUBAGENT_FAILED__:类名` 哨兵显式标记，保证失败信号不被吞 | 即使保留 spawn，也要求子 agent"无内容也算一种结果"，主代理必须有明确分支处理 |
| error-recovery skill（eliteai.tools） | **失败分类决策树 + 有限重试** | Transient（超时/畸形输出/空返回）→ 简单重试最多 3 次；仍失败 → 降级/升级；3 次以上或不可恢复 → 优雅终止并报告 | 我们已用掉 08-06、08-13 两次重试机会，空返回在**本环境是系统性而非偶发**，重试策略收益低，直接选"降级到同步" |
| cortex 子代理基类（HuggingFace 开源） | **两次尝试 + empty_fallback** | 首次失败 → 携带原文续写重试一次 → 仍失败 → 合成"低置信度"空结果，保证调用方永远拿到结构化对象而非异常 | 主代理自审就是我们的 empty_fallback，且置信度不降（主代理持有全部工具） |
| yoyo-evolve analyze-trajectory | **失败后直接读共享状态自审** | 子 agent 不可用时，主代理读取共享状态（日志文件），在主上下文内自己分析，输出标记 `confidence: low` | 与"文件系统即通信通道"同源；项目 `orchestrator.py` 已经践行此模式（中间状态通过文件传递，便于调试和恢复） |

**调研结论**：业界共识是"给失败留显式降级路径"，而非"祈祷子 agent 一定成功"。对本项目，最贴合、最省事的组合是——**默认同步（方案A）+ 空返回降级规则（方案C）+ 文件落盘兜底（方案B，可选保留双 Agent 叙事）**。

## 4. 方案对比

| 方案 | 描述 | 优点 | 缺点 | 评级 |
|------|------|------|------|:---:|
| A. 主代理同步审校（推荐） | 取消 spawn，阶段2 由主代理跑 `validate_article.py` + 人工对照 CHECKLIST/FORBIDDEN + 最小结构验证 | 零异步依赖、永不卡等待、已 08-13 实测可行（约 1 分钟） | 失去"独立视角"（可加脚本规则扫描器补） | ⭐ 首选 |
| B. 保留双 Agent + 文件落盘兜底 | 子 agent 把报告写入 `articles/{日期}-reviewer-report.json`，主代理 Read 文件，不依赖消息回传 | 保留"双 Agent"叙事；结果持久化可审计 | 本环境子 agent 写文件也可能失败；仍可能卡在 spawn 调用本身 | 可选 |
| C. spawn + 空返回立即降级 | 保留 spawn，但把"空返回/非 JSON"列为必须处理的显式分支：立即放弃子 agent，切主代理自审 | 改动小 | 阻塞调用本身仍可能卡（13:57 教训），降级前提是主代理能拿到工具返回 | 兜底规则 |
| D. 纯脚本流水线 | 阶段2 完全由 `run_pipeline.py`/`orchestrator.py --phase2` 执行，AI 只做 CHECKLIST/FORBIDDEN 语义层 | 机械步骤零 token | 语义层（FP 扫描、判断）仍需 AI；脚本不可用时要回退 | 增强项 |

**最终推荐：A 为主 + C 作防御性规则 + D 作为可复用脚本手段（validate/auto_fix 已经是脚本），B 仅当 Master 想保留双 Agent 叙事时启用。**

## 5. 推荐方案：同步式审校（v2 落地版）

### 5.1 新阶段2 流程（主代理同步完成，五步）

1. **脚本审核**：运行
   `python F:/WorkBuddy/daily-why/scripts/validate_article.py --json "{初稿路径}"`
   记录 P0/P1/P2 数量与得分。
2. **自动修复（可选增强）**：若脚本报出可自动修复的格式项（Q 格式、分隔线数、反转标签、表格行数），运行
   `python F:/WorkBuddy/daily-why/scripts/auto_fix.py "{初稿路径}" --verify`
   （自动备份 .bak，修复后复验），再重跑步骤 1。
3. **人工对照 CHECKLIST**：`Read` 加载 `C:/Users/admin/.workbuddy/skills/daily-why-writer/references/CHECKLIST.md`，逐项扫描。
4. **人工对照 FORBIDDEN**：`Read` 加载 `.../references/FORBIDDEN.md`，逐条扫描【全部】FP 规则（数量以文件实际内容为准，不写死编号）。
5. **最小结构验证 + 就地输出报告**：A 段引用块（`>` 开头）、C 段 Q 格式（`**Q1/Q2/Q3：**`）、F 段引用块含"冷知识反转"标签、结尾四行风格表格，任一缺失即 P0。输出 Markdown 表格或 JSON 文本，含 `pass / p0_count / p1_count / p2_count / score / issues`（每项 level/category/description/suggestion）。通过条件：P0=0 且 P1≤2。

### 5.2 阶段3 相应简化

- 通过 → 直接输出。
- 不通过 → 按 issues 修复 → 重跑阶段2 审校（最多 2 轮，此时即重跑步骤 1 到 5，不再 re-spawn）。
- 2 轮后仍不通过 → 标记"⚠️ 需人工审核"，输出当前最佳版本。

### 5.3 异常表新增口径（防御性）

| 场景 | 处理 |
|------|------|
| validate_article.py 执行失败 | 先 `auto_fix.py --verify` 修复再重试；仍失败则记录错误并继续人工对照，不阻塞流程 |
| （防御性）历史遗留 spawn 的子 agent 空返回 / 非 JSON | 立即放弃该子 agent，切主代理自审（见 5.1），记录"⚠️ 审校降级为主代理自审"，流程继续，不等待重试 |
