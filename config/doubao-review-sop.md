# 豆包审阅标准操作流程（SOP）

> 版本：v1.0 | 创建：2026-08-26
> 用途：每日冷知识文章的"豆包审阅"环节标准化执行指南
> 触发口令：**「今日豆包审阅」**

---

## 一、触发与前置检查

用户说出触发口令「今日豆包审阅」后，**第一步必须运行脚本预检**，禁止跳过。

### 1.1 运行完整预检

```bash
C:/Users/admin/.workbuddy/binaries/python/versions/3.13.12/python.exe F:/WorkBuddy/daily-why/scripts/doubao_review.py --all
```

### 1.2 根据退出码判断

| 退出码 | 含义 | 动作 |
|--------|------|------|
| 0 | 预检通过，文章存在 | 继续执行审阅 |
| 1 | 未找到项目目录 | 报告「当前可能不是工作电脑，未找到 F:\WorkBuddy\daily-why」，**终止** |
| 2 | 周末 | 报告「今日周末，无文章」，**终止** |
| 3 | 今日文章不存在 | 报告「今日文章尚未生成」，**终止** |
| 4 | 参数错误 | 检查命令，重试 |

### 1.3 检查豆包.txt 是否已填充

预检输出中 `doubao_filled` 字段：
- `false` → 正常执行审阅
- `true` → 提示用户「今日豆包.txt 已填充（X 字节），是否覆盖？」，等待用户确认后再执行

---

## 二、执行步骤

### Step 1：读取文章全文

从预检输出的 `article.path` 字段获取文章路径，用 `Read` 工具读取全文。

**必须读取完整内容**，不得凭摘要或印象审阅。

### Step 2：执行审阅（核心环节）

按以下固定结构输出审阅内容，**三部分缺一不可**：

```
## 一、优缺点分析

**优点**
1. ...（至少3条，每条具体指出好在哪里、对应原文哪个位置）
2. ...
3. ...

**缺点/硬伤**
1. ...（每条包含：问题描述 + 具体表现 + 影响）
2. ...
3. ...

## 二、优化方向

1. ...（每条是可执行的优化动作，不是空泛建议）
2. ...
3. ...

## 三、优化后版本

# {标题}

{完整优化后的文章正文}

---

| 速记卡 | 内容 |
|--------|------|
| ... | ... |
```

### Step 3：写入豆包.txt

将 Step 2 的完整输出写入：
```
F:/WorkBuddy/daily-why/投喂素材/{YYYYMMDD}/豆包.txt
```

- `{YYYYMMDD}` 从预检输出的 `date` 字段转换（如 `2026-08-26` → `20260826`）
- 使用 `Write` 工具，**完整覆盖写入**
- 写入前确认文件夹存在（预检已确认）

### Step 4：回读验证

写入后立即用 `Read` 工具回读豆包.txt，验证：
1. 文件非空
2. 三部分结构完整（优缺点分析 / 优化方向 / 优化后版本）
3. 优化后版本包含标题和正文
4. 无截断、无乱码

### Step 5：报告完成

向用户报告：
- 文章标题
- 原文字数 / Q数
- 豆包.txt 路径
- 审阅要点摘要（1-2句话）

## 三、豆包审阅风格定位

基于历史投喂记录（`投喂素材/AI能力特点.md`），豆包的稳定特点是：

### 3.1 核心优势（必须发挥）

1. **机制严谨度基准**：术语准确，逻辑链补全最稳。对物理/生物机制的表述精度敏感，善于抓"不是A而是B"类绝对否定表述。
2. **因果闭环补全**：主动桥接前一Q段的实验与后一Q段的机制，让因果链不断裂。
3. **结构层级敏感**：对生物结构层级/数量混淆（如刚毛数≠接触点数）高度敏感，擅长抓事实精度。
4. **概念分层修正**：善于区分"现象存在/明显/可感知"等不同层面，避免笼统表述。
5. **实用场景覆盖**：个体差异、日常应用、安全提示补全最稳，表述稳妥不夸大。

### 3.2 常见越界（必须避免）

1. **不要改Q格式**：原文的 `**Q1：...**` 格式必须保留，不要改成自然段落或其他格式。
2. **不要删结尾表格**：原文的风格说明表格是 A+C+F 结构的一部分，不要删除或改成"信息卡片"。
3. **不要改标题结构**：不要把疑问句改成陈述句，不要去掉 emoji。
4. **不要超字数**：优化后版本控制在 600-800 字，不要扩到 1000+ 字。
5. **不要加互动CTA**：不要加"评论区告诉我""你觉得呢"等格式外内容。

### 3.3 审阅时的豆包视角

- 优先抓**机制表述精度**和**因果链完整性**
- 对**绝对化表述**（"完全""根本""所有"）保持敏感，主张用"以XX为主、XX为辅"的相对表述
- 善补**个体差异**和**限定条件**，让结论更稳妥
- 优化版中保持原文的 A+C+F 结构（A段引用块引入 → C段Q&A → F段冷知识反转+表格）

## 四、输出格式规范

### 4.1 与其他AI文件的一致性

豆包.txt 的格式必须与同目录的 ds.txt、ima.txt 保持一致：
- 第一部分：`## 一、优缺点分析`
- 第二部分：`## 二、优化方向`
- 第三部分：`## 三、优化后版本`
- 使用 Markdown 格式
- 中文标点

### 4.2 优缺点分析的写法

**优点**：每条格式为 `**关键词**：具体描述（对应原文位置/证据）`
- 至少3条，不超过6条
- 必须具体，不能写"写得好""有趣"这类空泛评价

**缺点**：每条格式为 `**问题类型**：具体表现 + 影响 + （可选）修正方向`
- 至少3条，不超过8条
- 区分"硬伤"（事实错误、逻辑断裂）和"软伤"（表达可优化、节奏可调整）
- 科学准确性问题必须标注级别

### 4.3 优化方向的写法

- 每条是**可执行的动作**，不是空泛建议
- 与缺点一一对应或合并归纳
- 格式：`动词 + 具体内容`（如"开头换量化反差""Q2加生活化类比"）

### 4.4 优化后版本的写法

- 保留原文的 A+C+F 结构
- 标题可优化但必须保留疑问句形式和 emoji
- 字数 600-800 字
- Q数与原文一致（通常3Q）
- 结尾保留速记卡/风格表格
- 优化是**重写**，不是在原文上改几个词——但核心科学结论必须与原文一致，不得改变事实

## 五、异常处理矩阵

| 异常场景 | 检测方式 | 处理方式 |
|----------|----------|----------|
| 不是工作电脑 | 脚本退出码1 | 报告路径未找到，终止，不执行任何写入 |
| 周末 | 脚本退出码2 | 报告周末无文章，终止 |
| 文章未生成 | 脚本退出码3 | 报告文章不存在，提示稍后重试，终止 |
| 豆包.txt已填充 | 预检 doubao_filled=true | 询问是否覆盖，等待确认 |
| 文章读取失败 | Read工具报错 | 重试1次，仍失败则报告错误并终止 |
| 写入失败 | Write工具报错 | 检查路径权限，重试1次，仍失败则报告错误 |
| 回读验证发现截断 | Read回读内容不完整 | 重新写入，再次验证 |
