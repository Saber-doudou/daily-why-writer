## 二、今天两次 push 失败的根因（决定 R8 要不要前移）

读代码 + 实测后的结论，与初版判断不同，先摆事实：

### 根因 D1：探活失败被当成结论，而不是「再试一次的信号」

`l3_publish.git_pull_rebase_push` 第 175 至 179 行：

```python
for attempt in range(retries + 1):
    if attempt > 0:
        if not github_reachable():
            return False, "网络失败（不可重试）：github.com 探活失败…"
```

`github_reachable()` 是**单次** `curl`（连接超时 8 秒）。实测在本机每次耗时 1.7 到 2.8 秒，属真实网络调用，会偶发失败。**一次 curl 抖动，整条重试链直接放弃**，而且给出的结论是「不可重试」。

这与设计意图相反：探活本意是「先确认网络通再花时间重试」，现在变成了「探活本身就是裁判」。今天 14:00 报的 `git_sync=fail` 即此，随后手工 `git push` 立刻成功。

### 根因 D2：「工作区脏」被误报成「rebase 冲突」

`classify_git_error` 只认 network 与 conflict 两类关键词，其余全归 `other`；`other` 落到 abort 分支后，统一打印「rebase 冲突」。今天第二次失败的真实 stderr 是：

```
cannot pull with rebase: You have unstaged changes.
```

既不是网络问题，也不是冲突——是工作区有未提交改动。结果却报成冲突，还顺手执行了一次无意义的 `rebase --abort`。

### 所以 R8 该不该前移

**不该。** R8 的资产是 `retry_policy.py`（通用重试：429 自动恢复、指数退避加抖动、幂等、无重复 IMA 笔记），判据是「429 自动恢复 / 无重复笔记」。今天的痛点是**这道门写错了 30 行**，不是缺一套策略。用 R8 去解决它属于大锤砸小钉，而且会把 R5 金集的建设往后推。

改法：另开 **R3.8（0.5 人日）**，只做两件事：

1. 探活本身重试 3 次（间隔 2s / 5s），全失败才判不可达；且探活失败时**仍尝试一次真实 push**——探活只该用来省时间，不应当裁判。
2. `classify_git_error` 增加 `dirty` 类（匹配 `unstaged changes` / `your local changes`），报告「工作区有未提交改动」且**不执行** `rebase --abort`。

## 四、每一轮都要加的「送达检查」（从 #67 学到的）

这是本方案的核心改动，不只是调顺序。

**问题**：13 轮的验收判据都是「本地有个文件、本地自检绿」。但交付物要经过 `extra_sync` → `git_add_files` → 镜像仓库 → GitHub 四道关，任一环漏了就静默丢失。

**现有三道检查为什么都覆盖不到**：

| 检查 | 它查什么 | 漏在哪 |
|---|---|---|
| Phase 3 双向自检 方向一 | 白名单里的每项有没有复制源 | 只管「清单内」，不管「该进清单的有没有进」 |
| Phase 3 双向自检 方向二 | 已跟踪文件在不在白名单 | 同上，且只看已跟踪的 |
| `full_selfcheck` | 本地脚本与配置 | **从不读镜像仓库** |

**R3.9 要查的是第四面**：三方名单一致。

```
① 本轮声明的交付物清单（轮次记录里显式列）
② 两份白名单（config 的 git_add_files + l3_publish 的 extra_sync）
③ 镜像仓库实际存在（git cat-file -e）
```

缺一即 exit 1 并指名缺哪项。

**远端校验做成可选**：网络不通时不能让它把轮次判红——那会变成新的假失败（正是今天 D1 的教训）。默认只查本地镜像，加 `--remote` 才查 GitHub。

**为什么值得单独立一轮**：R2/R3 加起来约 8 人日的产物，在仓库里**一个字节都没有**地存在了一整天，而所有自检都是绿的。而 R4 至 R13 预计再新增十来项资产（`run_report.py`、`eval_runner.py`、`rule_index.json`、`stage_runner.py`、`retry_policy.py`、向量库、模型档位配置、注入隔离、规则元数据、`sync_version.py`），每一项都是一次「可能忘了进两份白名单」的机会。

## 六、验收判据的补充（对每一轮都适用）

原方案书的判据只有「通过」和「停止」两栏。补四条：

1. **送达检查必须绿**（R3.9 落地后强制），否则本轮不算完成。
2. **性能/质量类断言必须带「怎么测出来的」**。反例：今天 S4 的 `s2_seconds=146` 含人工思考与联网往返，和 S1 的 21.1s 不可横向比较。R4 落地后统一用脚本计时。
3. **新增夹具必须断言「理由」而不只是数量**（#68 教训）。`evidence_gate` 已改成 `expect_codes`，后续轮次照此办理。
4. **凡「外部依赖失败」的判定，必须区分「真的不行」与「这一下没成」**（今天 D1 教训）。探活、限额、超时这类检查，单次失败不能当结论。
