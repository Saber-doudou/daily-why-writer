## 三、每一轮都要加的「送达检查」（从 #67 学到的）

这是本方案的核心改动，不只是调顺序。

**问题**：13 轮的验收判据都是「本地有个文件、本地自检绿」。但交付物要经过 `extra_sync` → `git_add_files` → 镜像仓库 → GitHub 四道关，任一环漏了就静默丢失。

**做法**：R3.9 做一个 `delivery_check.py`，每次轮次收尾必跑，检查三方一致：

```
① 本轮声明的交付物清单（新轮次必须在轮次记录里显式列）
② config/scripts 两处白名单（git_add_files + extra_sync）
③ 镜像仓库实际存在 + 远端实际存在
```

三者缺一即 exit 1，并指名缺哪一项。

**为什么值得单独立一轮**：R2/R3 加起来约 8 人日的产物，在仓库里**一个字节都没有**存在了一整天，而所有自检都是绿的。这类失败的概率不低、发现成本极高（要靠人偶然去比对目录）。

## 五、验收判据的补充（对每一轮都适用）

原方案书的判据只有「通过」和「停止」两栏。补三条：

1. **送达检查必须绿**（R3.9 落地后强制），否则本轮不算完成。
2. **性能/质量类断言必须带「怎么测出来的」**。反例：今天 S4 的 `s2_seconds=146` 含人工思考与联网往返，和 S1 的 21.1s 不可横向比较。R4 落地后统一用脚本计时。
3. **新增夹具必须断言「理由」而不只是数量**（#68 教训）。`evidence_gate` 已改成 `expect_codes`，后续轮次照此办理。
