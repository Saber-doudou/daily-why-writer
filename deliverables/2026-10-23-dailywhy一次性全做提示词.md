# dailywhy 一次性全做提示词（总控版）

> 版本：v1.0
> 日期：2026-10-23
> 用途：Master 把下面整段提示词发给执行人；执行人按 R1 到 R13 全做，自己拆分工作与审校，不逐轮等确认
> 配套：方案书 v1.3、执行清单 v1.1、交接 README、执行提示词包

---

## 使用说明

- 把下面「总控提示词」整段复制给执行人（或他的 AI 会话），**只需要这一段**。
- 执行人自己负责：每轮开新工作会话、每轮另开只读审校会话、逐轮记录、最后汇总。
- 只有触发「停止条件」时，执行人才需要回来找 Master；否则一次性做完 13 轮。
- 如果执行人问"为什么要分开"，回答：避免 13 轮上下文互相污染，避免自己改自己评。

- 每一轮开一个新的工作会话，只带本轮任务卡与上一轮验收记录，不要把 13 轮塞进同一个上下文。
- 每一轮另开一个只读审校会话，工作会话不得自评。
- 如果无法新开会话，用 /clear 或新建任务，确保不带上一轮的推理过程。

【一、开工前读什么】
按顺序读：
1. F:/WorkBuddy/daily-why/deliverables/dailywhy-优化交接包-20261022/README.md

【二、开工前核对，不改代码】
在工作空间 F:/WorkBuddy/daily-why 下运行：
1. C:/Users/admin/.workbuddy/binaries/python/versions/3.13.12/python.exe scripts/full_selfcheck.py
   确认基线 20/24，记录 4 个失败项。

   确认三态正常。
3. 看 l3_run.log 最后 30 行，确认最近一次发布正常；如果最近一次发布失败，先停下报告，不要开始优化。
4. 确认 09:40 的 L1 自动化仍在 main 上跑。
5. 建/切换到分支 auto-optimize/dailywhy-20261022；如果已存在就继续用。
6. 建目录 deliverables/dailywhy-优化执行记录/，用于放每轮验收记录。

【三、按 R1 到 R13 串行执行】
顺序固定：R1 → R2 → R3 → R4 → R5 → R6 → R7 → R8 → R9 → R10 → R11 → R12 → R13。
不许跳轮、不许并行、不许合并轮次。每天最多推进 2 轮，保证每轮独立审校质量；不要为赶进度压缩验收。

每天开工前：先看当天 09:40 的 L1 是否正常产出；不正常先停下报告，不要开始当天的优化。

每一轮严格按下面 8 步：
1. 开一个新的工作会话（新上下文），只贴：
   - 本轮任务卡（用提示词包的提示词 2 模板填好）；
   - 上一轮的 1 页验收记录；
   - 本轮相关的方案书/执行清单段落。
   不要贴 13 轮全文，不要把历史对话带进来。
2. 诊断：用数据说明当前最低指标，不用印象。
3. 只改一个资产；改动前先 commit 留基线。
4. 跑本轮验收命令；命令与真实输出逐条保存。
5. 另开一个只读审校会话（新上下文），贴：
   - git diff；
   - 验收命令与真实输出；
   - 本轮验收口径。
   用提示词包的提示词 3 审校；工作会话不得自评。
6. 审校 verdict=keep → commit，记 results.tsv；verdict=revert → git revert HEAD，记 results.tsv，本轮结束，进入下一轮。
7. 写 1 页验收记录到 deliverables/dailywhy-优化执行记录/R{N}-验收记录.md（用提示词 4 格式）。
8. 进入下一轮。不要回头重做已 keep 的轮次，除非后面轮次证明它导致了回归。

【四、停止条件】

- 日更中断：L1 连续 2 天没有产出或发布失败。
- 数据丢失：历史文章、review JSON、config 被删除或覆盖。
- 凭据泄露：token、API key、IMA ID 被提交或写进日志。
- 同一轮连续 2 次验收失败，或 2 次审校 revert。
- 需要做 D-01 到 D-05 之外的决策（改范围、改内容标准、改预算）。
- 单轮耗时超过执行清单估算的 2 倍，或成本超过上一轮 2 倍。
- 出现无法归因的回归（金集指标下降但找不到原因）。

遇到以下情况，只停本轮，不回滚已 keep 的轮次：
- 单次验收失败：允许修一次；再失败就 revert 本轮，记录，进入下一轮。
- 单次审校 revert：直接 revert 本轮，记录，进入下一轮。
- 某轮资产缺少依赖（例如 R5 需要 R2 的 schema）：先补依赖，再继续；不要跳过验收。

2. F:/WorkBuddy/daily-why/deliverables/dailywhy-优化执行记录/results.tsv
   每轮一行，字段：timestamp / commit / asset / old_score / new_score / status / dimension / note / eval_mode。
3. 一份给 Master 的合并检查清单：哪些轮次 keep、哪些 revert、合并前要跑哪三条命令、合并后如何回滚。

【六、硬约束】
- 不改 main；所有改动留在 auto-optimize/dailywhy-20261022 分支。
- 不直接改 09:40 的 L1 自动化 prompt；不调用 automation_update；prompt 替换只能由 Master 在合并后做。
- 不提交 scripts/config.json；git add 前先看 git status。
- 一次只改一个资产；不用 git reset --hard；回滚用 git revert。
- 不做多 agent 编排；每轮只允许一个只读 Reviewer 子 agent（没有 spawn 就开独立会话）。
- 不并行跑轮次；不把 13 轮塞进一个上下文。
- 不伪造命令输出；没有跑过的命令写"未运行"，不写"已通过"。
- 不删除、不移动历史文章与 review JSON；不修改已发布文章的归档。
- 不擅自改 D-01 到 D-05；需要变更时停下问 Master。

【七、开始】
先复述四件事，确认你理解一致：
1. 本次总目标与 13 轮顺序；
2. 三条绝对不能碰的东西；
3. 什么情况必须停下找 Master；
4. 每轮如何分开做、分开审校。

复述一致后，从 R1 开始，不要等 Master 再确认。

## 执行人可能会问的三个问题

**Q1：为什么不一次在一个会话里做完？**
13 轮共用上下文会互相污染：前面的失败尝试、废弃方案、临时判断会被后面的模型当成事实；上下文越长，注意力越散。分开做，每轮只带本轮任务卡与上一轮验收记录，才能保证归因清楚。

**Q2：为什么每轮要另开审校会话？**
自己改自己评，等于同一套先验既写又审。独立会话只看 diff、命令输出和验收口径，能抓到"执行人以为对、其实没跑"的情况。这是 maker-checker 的最低成本落地。

**Q3：中途发现方案有问题怎么办？**
不要擅自改方案。记录证据，触发停止条件，回来找 Master；由 Master 决定改 D-01 到 D-05 还是调整本轮资产。
