### 4.3 根因：两处独立断裂 + 一处可救点

今日文件 `投喂素材/20260917/学习总结.md` 的逐条归因（实测输出）：

| 章节标题 | 去序号后首段 | 是否以关键词开头 | 正文字形态 |
|----------|--------------|------------------|------------|
| `## 一、四 AI 核心差距与采纳/拒绝决策` | 「四 AI 核心差距与采纳/拒绝决策」 | ❌ 关键词「核心差距」在**中部** | **表格 8 行 / 列表 0 项** |
| `## 二、事实核查结论（…）` | 「事实核查结论（…」 | ❌ | 列表 5 项 |
| `## 三、v2 改写要点（…）` | 「v2 改写要点（…」 | ❌（**含可救的 6 项编号列表**） | 列表 6 项 |
| `## 四、规则沉淀（…）` | 「规则沉淀（…」 | ❌ | 列表 6 项 |
| `## 五、遗留 / 待观察` | 「遗留 / 待观察」 | ❌ | 列表 3 项 |

**断裂 ①（今日命中）标题锚点必须「以关键词开头」。**
pattern 2 的正则结构是 `^##\s*(可选中文序号)?(采纳清单|改进点|优化点|核心差距)`，即关键词必须紧跟在「`## ` + 可选序号」之后。今日标题把关键词放在中部且与「采纳」用「与」并列（`四 AI 核心差距与采纳/拒绝决策`），两条 pattern 全部不匹配 → 0 命中。
（08-11 二轮的 `## v2 → v3 改进点` 同理：关键词在，但 pattern 1 硬要 `v1 → v2`、pattern 2 硬要关键词在开头。）

**断裂 ②（今日未暴露但已存在）正文形态只认列表，不认表格。**
即使把标题锚点放宽让「一、」匹配上，该章正文是 **8 行 markdown 表格、0 个列表项**，`BULLET_RE` 只认 `- ` / `* ` / `1. ` 三种前缀 → **仍然返回 0**。
→ 这一点原判断没说，但它意味着：**只放宽标题正则仍不足以救回今天这份**。

**可救点 ③：`## 三、v2 改写要点` 的正文是 6 项编号列表，本来就能被 `BULLET_RE` 抽到**，只因标题不含四个关键词之一而从未被考虑。只要把「改写要点」纳入关键词，今天这份立刻能提出 **6 条**（实测：列表项=6）。这是个低成本高收益的切入点。

### 4.4 为什么「已根治 / 已修好」两次判定都失准

| 时点 | 当时的判定 | 失准原因（本次查证） |

## 五、附带发现：此前未记录的新缺陷

### `scripts/config.json` 死条目 + `git add` 静默失败 + 双向自检假绿

| 检查项 | 实测 | 命令 |
|--------|------|------|
| repo 内文件存在 | True | 文件系统 |
| 是否被 gitignore | **是**，`.gitignore:2  scripts/config.json` | `git check-ignore -v` → rc=0 |
| `git add` 是否成功 | **否**：`The following paths are ignored by one of your .gitignore files` | `git add -n` → rc=1 |
| 是否被 git 跟踪 | **否** | `git ls-files --error-unmatch` → rc≠0 |
| 最后一次提交 | `ea6465e security: gitignore scripts/config.json (含 IMA KB ID)` | `git log -- scripts/config.json` |
| 是否出现在灰区告警 | **否**（灰区算的是 `tracked - whitelist`，它未跟踪 → 隐身） | Phase 3 自检逻辑 |
| Phase 3 双向自检是否告警 | **否**，报「白名单全覆盖，无灰区文件」 | 今日报告 Phase 3 行 |

**成因链**：某次为安全（含 IMA KB ID）主动把 `scripts/config.json` 写进 `.gitignore`，但**没有同步把它从 `config.json` 的 `git_add_files` 里摘掉**。于是：

1. Phase 3 的 `extra_sync` 仍把它**复制进 repo 工作区**；
2. `git add scripts/config.json` 被 git 拒绝，而调用处是 `subprocess.run(..., capture_output=True)`，**返回码与非空 stderr 都被丢弃** → 静默失败；
3. 双向自检只校验「白名单项有没有**复制源**」，不校验「git 是否真的 add 成功」→ 报「全覆盖」；
4. 反向灰区检测算的是 `tracked - whitelist`，未跟踪文件不在 `tracked` 里 → 也不报。

**两头都不报 = 完美隐身。** 与缺陷 #46（CHANGELOG.md 在 `git_add_files` 却从未提交）同款，区别是 #46 被查出来了，这条被 `.gitignore` 挡住了视线。

**风险定性：低。** 不会导致发布失败，也不会泄露（`.gitignore` 正是拦截它的那道闸）。真正的危害是**假绿**：自检声称「全覆盖」，实际白名单里躺着一条永不生效的死条目。命中「死文件判据」（谁读？哪步读？答不出）。
