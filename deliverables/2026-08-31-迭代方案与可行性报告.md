## 1. V2 优化版独立审校（重点评估阻塞风险）

### 1.1 现状

L2（feed-learning）产出优化版 v2 后，目前**只跑 `validate_article.py` 脚本审核**（P0=0 且 P1≤2 即过），没有独立 Reviewer。而 v2 恰是**最终发布版本**——它反而是唯一没有独立视角校验的产物。

### 1.2 方案设计

在 L2 SKILL.md 的 v2 重写步骤后插入独立审校（复用 L1 已验证的 v2.0 模式）：

```
v2 写入后 → spawn 独立 Reviewer（general-purpose + reasoning，禁传 name）
   ├─ 审校对象：优化版文件（复用 L1 的 9 步审校模板：脚本+CHECKLIST+FORBIDDEN+事实核验+分级）
   ├─ 报告落盘：review/{date}_v2_review.json   ← 与 L1 的 {date}_review.json 分离，不覆盖
   ├─ 通过条件：P0=0 且 P1≤2
   ├─ 熔断：spawn 失败 / 15min 超时 → 降级为现有脚本审核，标记「⚠️ v2 未独立审校」，继续
   └─ 修复：不通过 → 修复重试最多 2 轮 → 仍不过 → 「⚠️ 需人工审核」输出当前最佳版本
```

### 1.3 阻塞风险评估（Master 核心问题）

**结论：不会造成新的阻塞。** 四条防线：

| 风险 | 现有防护 | 新增防护 |
|---|---|---|
| spawn 失败 | L2 已有「审核不通过→修复 2 轮→兜底」 | 熔断降级为脚本审核（=现状），**不阻塞** |
| Reviewer 卡死 | 无（新增） | 15 分钟显式超时，超时按熔断 |
| 审校不通过死循环 | 已有「2 轮后仍不通过→需人工审核」 | 同左，复用 |
| 与 L1 报告冲突 | 无（新增） | **文件名分离** `{date}_v2_review.json`，不覆盖 L1 记录 |

**唯一代价**：L2 时长增加约 5 到 8 分钟（L1 的 spawn 审校实测约 2 到 5 分钟 + 轮询），L2 从约 10 分钟变为 15 到 18 分钟。L2 是 Master 手动触发的会话流程，无准点要求，可接受。

### 1.4 附加收益

- v2 的得分从此有 Reviewer 综合分（目前只有脚本分）→ 仪表盘 `v1→v2` 两列口径终于一致（都含人工）
- 仪表盘 6 列表头恢复后，v2 列也终于有真实意义

### 1.5 改动量

- `daily-why-feed-learning/SKILL.md`：新增「v2 独立审校」小节（约 30 行）
- 无脚本改动（spawn 是 Agent 工具行为，由 SKILL.md 指令驱动）
- 注意：L2 完成后把 v2 的 score 记入仪表盘 v2 列（替换现在的脚本 100）

## 2. 发布报告脚本渲染

### 2.1 现状

发布报告（`deliverables/{date}-发布报告.md`）是 **AI 手写 markdown**——08-31 已实证数据失真（字数 452/601 vs 实测 377/525、规则同步虚报）。

### 2.2 方案设计

`l3_publish.py` 新增 `render_report()`，在 `res.summary()` 前调用：

```
数据源（全部已有）：
  - v1_meta / v2_meta  → 话题、分类、字数（chinese_chars）、Q数
  - ima_result / git_result → note_id、commit hash
  - res.phases         → 每个 Phase 的编号/状态/消息（Result 类已收集，第 42 行）
  - res.errors/warnings → 汇总状态

输出结构：
  # 发布报告 — {date} {topic}
  ## 基本信息（meta 自动填）
  ## 执行结果（res.phases 逐条渲染：Phase 0/1/2/3/4/5 的状态 + 消息）
  ## 汇总（errors/warnings 计数）
  ## AI 语义验证补充区（占位符，AI 把 Step 2 的改进点表格填进来）
```

### 2.3 关键决策

- **语义验证表格（Step 2 的改进点→证据）是 AI 语义层产物，脚本无法生成**。处理：脚本渲染骨架 + 末尾留「AI 补充区」，AI 只需追加语义验证表，**不再手写基本信息和数字**（杜绝失真源头）。
- 报告在 main() 内自动写入，AI 不再自己编文件。

### 2.4 改动量

`l3_publish.py` +60 行（render_report 函数 + main() 两行调用）。风险：低。

## 3. automation memory 分片

### 3.1 现状

`automation-1778312519754/memory.md`：**1366 行 / 104 个日期条目**（05 月至今，最新在前），L1 每次启动**全量读入**——11 分钟耗时的主要嫌疑点（08-27 执行时 AI 已抱怨「文件过大，先获取行数再读」）。

### 3.2 方案设计

**一次性归档 + 读取约束，两步**：

```
Step 1（一次性）：把 2026-06-30 及更早的日期条目移到
   memory_archive_2026H1.md（同目录，首部加索引：日期范围+条目数）
   主文件保留 07-01 至今（约 500 行，可读）
Step 2（固化）：automation prompt 加一行硬约束
   「读取 memory.md 时用 tail -n 120 只读尾部；查更早历史再读归档文件」
```

### 3.3 风险与对策（已核实）

| 风险 | 核实结果 | 对策 |
|---|---|---|
| 有代码硬编码引用旧条目？ | ✅ 已 grep：prompt 只说「读取执行历史」，无硬编码行号/条目 | 无 |
| 归档切碎条目？ | 按 `^## 20` 日期标题切分，整条目迁移 | 脚本按标题行分界 |
| 归档后找不到历史？ | 归档文件带索引 + 同目录 | prompt 写明路径 |

### 3.4 改动量

- 归档：一次脚本执行（约 15 行 python）
- prompt：`generate_prompt.py` 加一行 + `--update-automation` 重新入库
- 风险：低

## 4. L3 独立日志恢复

### 4.1 现状

### 4.2 方案设计

`Result` 类加日志写入（最小侵入）：

```
class Result:
    def __init__(self, log_path="F:/WorkBuddy/daily-why/l3_run.log"):
        ...
    def _log(self, phase, status, msg):    # 追加一行
        [2026-08-31 15:30] [Phase 3] ✅ commit=xxx
```

- 追加模式（不覆盖历史）
- utf-8 编码
- 每次运行带时间戳分隔线，便于按次定位

### 4.3 改动量

`l3_publish.py` Result 类 +15 行。风险：低。
