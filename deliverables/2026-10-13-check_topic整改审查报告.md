## 二、应该处理（🟡，本次不阻塞，建议排期）

### 🟡 1. 单字 specific 的误杀面比披露的更宽（建议 Master 尽快决策）

执行人披露了「为什么盐能让雪融化」会被误拦。我实测发现**误杀面更宽**：

```
$ check_topic.py --angle "为什么汗水是咸的？"
❌ 重复: 概念重叠 [topic_summaries]: "为什么海水是咸的？" — 概念[海水咸]
   双侧命中现象词（新话题: 咸；已有: 咸），判重复（--angle 不可覆盖）  exit=1
```

「汗水为什么是咸」是经典可写选题，语料中**未写过**（我已全库核查），一旦被提即遭硬拦，且拦截理由（「与海水是咸的重复」）具有误导性——Orchestrator 按 prompt 规则只能换候选，一个合法选题被无声踢出池子。

**根因**：`海水咸` 的 specific 含单字「咸」「盐」，中文子串匹配下单字现象词的精度不足以支撑「硬重复」判定。注意此偏差源自我任务书的 schema（我写了 `["咸", "盐分", "盐"]`），执行人是按章执行。

**建议（二选一，需 Master 定）**：
- **A（推荐）**：`海水咸` specific 收紧为多字词（如 `["盐分", "海水盐", "盐度"]`）或暂清空并注释「单字现象词误杀面大于收益，待月度复盘评估」。代价：I8 用例与验收 A3 回归为放行——A3 本就是合成用例（真实语料无「大海里有盐」条目），可接受；`牛排血水`/`关节痛天气` 两族 specific 全是多字词，不受影响。
- **B**：维持现状，把「汗水咸/融雪盐」补进已知边界。代价：生产 prompt 已上线，明日 09:40 起每个工作日都在可能误拦。

### 🟡 2. 决策日志两个叠加缺陷（可观测性工程质量）

我统计了 `logs/check_topic_decisions.jsonl`（34 行 / 465,802 字符）：

- **78% 的 matches 是 score=0.0 的噪声**（7092 条中 5541 条），单条最大 19,765 字符。日志目的是「漏判率/误杀率可度量」，零分条目对此零贡献。
- **截断按行数不按字节**：5MB 触发时约 382 行，而「保留最近 2000 条」≈ 26MB——**截断永不把文件压回 5MB 以下**，且此后每次 check_topic 调用都会全文件读取 + 重写（5MB 级 IO）。

**建议**：matches 只记 `score ≥ 0.3`（或 top-20）；截断改字节预算（如保留最近约 2MB）。不影响判定正确性（日志失败本就不影响退出码），但当前形态下日志越长越难用。

### 🟡 3. T3 步骤 9 把裸标题传进 shell，有引号/元字符脆弱性

prompt 要求跑 `check_topic.py --angle --exclude-date {日期} "文章首行标题"`。今日牛排标题含 ASCII 引号，bash 会把引号吃掉——纯属巧合相消（T2 的剥离集也会剥引号），但含 `$`、反引号、反斜杠的标题会被 shell 解释，最坏情况是命令注入。

**建议**：改用 `--file` 模式（我已实测可用）：
```
check_topic.py --angle --exclude-date {今天日期} --file "articles/{年月}/{今天日期}-每日冷知识-{关键词}.md"
```
双赢：彻底消除 shell 转义问题，且去掉「人工抄首行」步骤（少一个出错面）。步骤 3 的候选话题有同款脆弱性（既有模式），可一并改。
