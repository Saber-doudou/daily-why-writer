## 1. 问题背景与根因（已实证）

### 1.1 事件
2026-10-13 自动化选题，初选"生牛排渗出的红色汁液不是血是肌红蛋白"，`check_topic.py --angle` 返回：

```
✅ 通过: ⚠️ 角度相关（相似度 67%），请确认写作角度与已有话题不同
  [topic_summaries]: "为什么雪是白色的？"
```

实际该话题与 **2026-09-07 已写《为什么牛排里的血水其实不是血？》** 完全重复，但脚本毫无感知。当日文章已写、审校已跑，经人工质疑才拦截，最终废弃重做。

### 1.2 根因（双层）

**根因 A（主因，脚本算法结构性盲区）**：`check_topic.py` 语义相似度用**字符级单向包含率**（`check_semantic_similarity`，line 96-140）：取两话题去停用字后的字符集合，算"较短一方的字有多少出现在较长一方里"，阈值默认 0.70，角度区间 [0.50, 0.70)。

它对**字面字符高度重叠**的重复敏感，但对**同义改写 / 换专业术语**完全失明。

实证推演（本次事件）：
- 新查询核心字：`{生,牛,排,渗,出,红,色,汁,液,血,肌,蛋,白}`（13字）
- 已写话题核心字：`{牛,排,里,血,水,其,实}`（7字）
- 共有字仅 `{牛,排,血}`（3字），短方为已写话题（7字）
- 包含率 = 3/7 = **42.8%**，连 50% 角度下限都不到 → 直接判"未使用过"

进一步实证：即便用接近原标题的查询 `为什么切牛排时流出的血水根本不是血？` 去对 9-07 标题，算法也只给 **57%**（角度区间），**永远到不了 70% 硬重复阈值**。结论：该脚本对"同主题不同句式"设计上就拦不住。

**根因 B（次因，执行人判断失误）**：初选返回"67% 关联【雪是白色的】"时，执行人误判"只跟雪相关就是新话题"，未意识到 67% 是跟雪匹配的、对真正撞车的"牛排血水"毫无感知（42.8% 低于角度下限，根本没进候选列表）。正确做法：带角度提示时应核实候选是否撞某已写话题，而不只看提示关联的那个。

### 1.3 影响面
- 10-12 自动化也曾将"关节酸痛预测天气"作为落选候选回写素材池（未撞车，侥幸）；9-07 牛排文是第二次险些撞车，属高频漏判。
- 任何"换说法"式重复选题均可绕过：如"海水为什么咸"改成"大海的盐从哪来"、"橘子为什么分瓣"改成"柑橘果肉为啥一瓣瓣"。

## 2. 修复目标

1. **拦住同主题不同句式 / 换术语的重复选题**（治本，非头痛医头）
2. **保留对"几乎相同标题"的精确匹配能力**（现有逻辑不丢）
3. **零新增重依赖**（项目用隔离 venv，尽量不引入 jieba 等第三方分词；若引入须走 venv 安装流程）
4. **回归测试**：本次牛排案例必须被判重复（语义相似或角度相关）

## 3. 推荐方案：概念重叠检测 + 混合判定

### 3.1 总体思路
字符包含率对"换词"失效，根因是它看的是**字面字符**而非**语义概念**。修复核心是引入一层**概念级（实体级）重叠检测**：把话题归一为"概念集合"，用集合重叠替代字符包含。

新判定 = 现有字符包含率（保留） **OR** 概念重叠命中（新增）。任一判重复即重复。

### 3.2 概念抽取与同义归并

新增 `config/topic_concepts.json`：

```json
{
  "concepts": {
    "牛排血水": ["牛排", "血水", "肌红蛋白", "红色汁液", "渗出液", "purge", "牛排血"],
    "关节预报天气": ["关节", "关节痛", "关节炎", "风湿", "气压", "预报天气", "天气痛"],
    "海水咸": ["海水", "咸", "盐", "海洋盐度"]
  }
}
```

- `check_topic` 扫描 `topics_context.json` 的 `topics` 数组时，每条已写话题额外带 `concept` 字段（回填历史，见第5节）。
- 新话题用 `extract_concepts(text)` 在其文本中匹配所有 concept 的关键词，得到新话题的概念集合。
- 与每个已写话题的 `concept` 比对：`若新话题概念集合 ∩ 已写话题概念集合 的元素个数 ≥ 2` → 判重复（或角度相关，按集合大小降级）。

**为什么 ≥2 而非 ≥1**：单概念（如都含"牛排"）可能只是大类相同（牛排可讲血水、可讲熟成、可讲部位），≥2 个概念重叠才说明在讲同一具体现象。本例新话题命中 {牛排血水}，已写命中 {牛排血水} → 交集 1 个概念但**该概念下关键词重叠多**（牛排+肌红蛋白/血水），故判定再加一条：**同一概念内关键词重叠 ≥2** 也判重复。两种口径取 OR。

### 3.3 判定逻辑（伪代码）

```python
def check_concept_overlap(new_topic, existing_topics, concept_map):
    new_cs = extract_concepts(new_topic, concept_map)  # set of concept_id
    for ex in existing_topics:
        ex_cs = set(ex.get("concept_ids", []))
        shared = new_cs & ex_cs
        # 口径1：共享概念数 >= 2
        if len(shared) >= 2:
            return True, f"概念重叠 {shared}"
        # 口径2：同一概念内关键词重叠 >= 2
        for cid in shared:
            kw_overlap = keywords_of(new_topic, cid) & keywords_of(ex["topic"], cid)
            if len(kw_overlap) >= 2:
                return True, f"概念[{cid}]关键词重叠 {kw_overlap}"
    return False, ""
```

### 3.4 混合判定接入点
在 `check_topic()` 的"检查3：语义相似度检测"（line 231-259）之后，新增"检查4：概念重叠检测"，并入 `is_duplicate` 判定。角度模式同理：概念重叠但仅命中1概念且关键词重叠<2 时，归为"角度相关"提示而非硬重复。

## 4. 三方案对比与选型

| 方案 | 原理 | 能否拦住牛排案例 | 依赖 | 维护成本 | 结论 |
|------|------|----------------|------|----------|------|
| **S1 概念重叠检测**（推荐） | 概念表 + 集合重叠 | ✅ 能（牛排+血水系命中） | 零（纯 JSON 表） | 中（需回填历史 concept） | **采用** |
| S2 Jaccard 双向相似度 | 改分母用并集 | ❌ 不能（3/17=17.6%） | 零 | 低 | 否决（换术语仍失效） |
| S3 复用现有 keywords 字段 | 用 topics_context 已有 keywords 做重叠 | ⚠️ 部分（仅9-07等已填关键字的条目，覆盖率低） | 零 | 低 | 可作 S1 的补充数据源 |

**选型理由**：S2 仅改分母，对"换术语"无能为力（已实证 17.6%）；S3 依赖 keywords 字段覆盖率，多数历史条目无此字段；S1 引入显式概念表，唯一能从语义层拦住改写重复，且零第三方依赖、可解释、可回归测试。

> 注：S1 的 `topic_concepts.json` 可由 S3 的 keywords 字段作为初始种子自动生成，再人工补同义词。

## 7. 风险与回退

- **误杀风险**：概念表过宽会误判"同大类不同角度"为重复。缓解：采用 ≥2 概念重叠 或 同概念内 ≥2 关键词重叠的双重口径，并对单概念命中降级为角度提示而非硬杀。
- **维护负担**：概念表需随新话题增长。缓解：`prepare_topics.py` 写入新话题时自动抽概念建议，人工确认入库。
- **回退**：改动集中在 `check_topic.py` 新增函数 + 新 JSON，不删改原有逻辑；若出问题，删除检查4调用即可回退到现状（已知漏判但稳定）。
