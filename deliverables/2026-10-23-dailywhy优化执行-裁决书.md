## 2. A 组裁决

### A1｜历史 review 95% 不可达

**裁决：采用 A（schema 版本分流），并把「95%」替换为三个更硬的指标。**

不采纳 B（放宽到 12 字段）：会让未来的新文件也漏掉核心字段，闸门变软。
不采纳 C（修改历史）：会破坏审计链，且违反「不修改 review JSON」的硬约束。

**schema 分层**

| 文件类型 | 判定 | 必填字段 |
|---|---|---|
| v1 新文件 | 有 `schema_version: "v1"` | 原有 18 个字段 + `schema_version`，共 19 个 |
| legacy 历史文件 | 无 `schema_version` | `article_id`、`review_timestamp`、`score`（或 `pass`）、`p0_count`、`p1_count`、`p2_count`、`issues`（允许空数组或 null） |
| 未知版本 | 有 `schema_version` 但不是 v1 | 直接失败，不允许猜 |

**替换后的 R2 验收口径（三条全过才算过）**

1. **分类准确率 100%**：74 份历史 review 全部被正确分到 v1 或 legacy，0 误判；执行侧用规则脚本分类，独立审校抽 10 份人工复核。
2. **新文件通过率 100%**：R2 之后连续 10 份新 review 全部通过 v1 schema。
3. **历史零修改**：`git diff -- review/` 为空；历史缺口只记录到 `deliverables/dailywhy-优化执行记录/legacy_gaps.tsv`，不修复。

**理由**：P0-4 的目标是阻止未来的格式漂移，不是把历史改漂亮。历史文件的缺口是「过去没有契约」的证据，应该保留。

---

### A2｜publish_manifest 零存量

**裁决：采用 A（40 份历史 + 1 份新 manifest），R2 范围增加 manifest 生成。**

不采纳 B（逆向解析 42 份 Markdown）：超出 P0-4 范围，且逆向生成等于伪造历史。
不采纳 C（本轮只做 3 个 schema）：`publish_manifest` 是 4 个契约之一，缺一个就还是自由文本交接。

**R2 具体做法**

1. 历史回放降为 40 份：25 份 review + 15 份学习总结。
2. `publish_manifest` 作为新增产物：在 L3 的报告渲染处同时写出 `publish_manifest.json`，每次发布一份。
3. R2 内用 1 次 `l3_publish.py --dry-run --no-git --no-ima` 生成首份 manifest，校验 100% 字段齐备。
4. 如果 dry-run 无法生成，允许用一份基于真实发布报告数据的 fixture，标注 `fixture=true`；R3 首次真实发布后替换。

**替换后的 R2 验收口径**

- 25 份 review + 15 份学习总结：100% 分类正确；legacy 不修改。
- 1 份新 manifest：schema 100% 通过；字段与真实发布报告逐项对得上。
- R2 人日从 3 到 4 调整为 **4 到 5**，因新增 manifest 生成；不另开轮次。

## 3. B 组裁决

### B1｜工作区不是 git 仓库

### B2｜分支隔离不成立（硬阻塞）

**裁决：采用 B（影子工作区），用 `git worktree` 实现，不用整目录复制。**

执行侧说得对：主工作区就是生产，分支只是记录。继续在主工作区直改，R2 到 R13 每一轮都直接上生产，不能接受。

**具体落地**

```bash
# 1. 在主工作区（保持 main）创建影子工作区
git worktree add F:/WorkBuddy/daily-why-opt auto-optimize/dailywhy-20261022

# 2. 复制配置（config.json 被 gitignore，不会进 git）
copy F:\WorkBuddy\daily-why\scripts\config.json F:\WorkBuddy\daily-why-opt\scripts\config.json

# 3. 修改影子工作区的 config.json
#    base_dir = F:/WorkBuddy/daily-why-opt
#    articles_dir / 投喂素材_dir / memory_dir / memory_md_path 等同步指向 opt
#    git_repo_path 保持主镜像，但所有 L3 测试一律加 --no-git --no-ima
```

**运行规则**

- 主工作区 `F:/WorkBuddy/daily-why` 保持在 `main`，09:40 自动化继续读它；不要在主工作区切换分支。
- R2 到 R13 的所有改动、测试、L1 模拟都在 `F:/WorkBuddy/daily-why-opt` 里做。
- 影子工作区的 `config.json` 不进 git；测试 L3 时加 `--no-git --no-ima`，避免误推、误备份。
- 某一轮验收通过后，在**当天 09:40 之后、次日 09:40 之前**把该轮 commit 合并回 main；合并前跑一次影子工作区的 `full_selfcheck` 与金集冒烟。
- 如果 Windows 路径或技能目录导致 worktree 失败：退化为整目录复制 `F:/WorkBuddy/daily-why-opt`，用独立 config；原则相同，仍然不在主工作区直改。

**R1 的处置**

- R1 已通过独立审校与 21/24 自检，**暂不撤销**。
- 但今天 09:40 的结果尚未验证：截至 09:52 未见 10-23 文章，属正常完成窗口（通常 10:08 到 10:20）。
- **10:30 前复查**：若 10-23 文章未生成或 L1 报错，立即在主工作区 `git revert 2fdc384`，再排查；若正常，保留 R1，并把 R1 的 commit 作为影子工作区的基线。

**方案书 10.6 的修订**

原文「未合并的改动不影响 09:40 的 L1」不成立。改为：

> 分支隔离只对影子工作区成立。主工作区就是生产，09:40 直接读取主工作区文件；任何在主工作区的改动都会立即生效。R2 起所有改动在 `git worktree` 影子工作区完成，验收通过后择时合回 main。

### B3｜version.json 非法

**裁决：追认 `baseline_repair` 通道，不需要新建 R0。**

**规则**

- 触发条件：问题不属于任何轮次资产，但会污染基线或让门禁静默失效。
- 形式：单独 commit，`results.tsv` 记一行 `asset=baseline`、`status=baseline_repair`、`note=根因`。
- 约束：只修问题，不改行为；必须有独立审校；必须记录修复前后的 `full_selfcheck`；必须能单独 revert。
- 本次 `255983b` 符合，追认。

**裁决：SKILL.md 与 references 的改动，用文件级快照回滚；workspace 脚本仍用 git revert。**
