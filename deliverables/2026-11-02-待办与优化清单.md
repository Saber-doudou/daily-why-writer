## 二、待优化项

### P0-1｜v2 审校报告是空壳，机械校验没起作用

**现象**：`review/2026-11-02_v2_review.json` 只有 215 字节、10 个字段。

**证据**：

```
字段仅：article_id / review_timestamp / pass / p0_count / p1_count / p2_count /
        score / revised_after_review / issues
缺失（validate_review.py v1.4 判出 10 项）：
  schema_version、script_result、structure_score、
  fact_checks、quote_checks、mechanism_checks、attribution_checks、
  term_checks、gap_checks、title_checks
实测：validate_review.py 退出码 = 1，🔴 错误 11 项
```

**根因两条，第二条是我的责任**：

1. L2 SKILL v3.5 的 Phase 2 第 ⑨ 步「落盘后 schema 自检」**没执行**。该步明确要求
   `validate_review.py` 退出码为 0 才可继续，非 0 须把 errors 原文贴回子 agent 重 spawn（最多 2 轮）。
2. 我写的 `generate_prompt.py` 阶段 3 有一句「**或**标注 `revised_after_review: true`」，
   本意是「改了文章后，去更新 v1 review.json 的 char_count/structure_score **或**打这个标记」，
   结果被理解成「v2 审校可以只写一个带 `revised_after_review` 的最小文件」。
   **一个「或」字造了一个合法出口**，这正是 EXP-004 说的「文本约束不住行为」。

**影响**：v2 审校的 H2 闭环复核锚点失效；L3 会把「总体判定」打成 ❌ FAIL 但**不会自动中止**
（`all_ok=False` 只影响报告，硬阻断只走 `blocking` 那条引用门禁），靠 SOP 的「人工补验」兜。
今天 L3 大概率照常发布，但会留一份 FAIL 报告 —— 工具是对的，流程没拿它当门禁。

**建议动作**：

1. 收紧 prompt 措辞：把 `revised_after_review` 明确限定为「**仅用于更新 v1 review.json 的字段，
   不得用它替代 v2 审校报告**」，并写明 v2 报告必须过 `validate_review.py` 退出码 0。
2. 把「v2 报告不合规」从「报告里记 FAIL」升级为**硬阻断**：在 `l3_publish.py` 的
   `review_schema` 判 `ok=False` 时 `sys.exit(1)`（与现有 `blocking` 引用门禁同构）。
   判据：宁可当天不发，也不发一份审核链断掉的稿。
3. （可选）L2 SKILL ⑨ 步加「把 validate_review 的输出行追加到学习总结」，
   让「跑没跑」在产物里留痕。

**工作量**：改 prompt 措辞 5 分钟；L3 加硬阻断 20 分钟 + 2 条夹具；合计半天内。
**验收**：拿今天的 v2_review.json 跑 L3，必须在 Phase 1 就 exit 1 并指名缺哪 10 项。

### P0-2｜6 条 claim 全部是 `snippet_only`，事实核实停在摘要级

**现象**：`evidence/2026-11-02.gate.json` 的 6 条 P1 全是 `snippet_only`。

**证据**：`p1_count=6`，`findings` 里 C1 至 C6 六条 claim 逐个报「仅 snippet 级核实，高风险 claim 建议 fetch 原文」。

**根因**：`snippet_only` 现行只判 P1（warn），不阻断。C 方案后事实责任划归
「L2 + evidence_gate」，但 evidence_gate 对「只查了摘要」这件事只提意见、不设门槛。

**为什么现在不能直接升 P0**：升 P0 会把当前 100% 的稿子挡下来（今天 6/6 全中），
等同于把门禁变成常闭。需要先解决「fetch 原文的成本与成功率」，否则就是用一个不可能达标的
标准把生产线停掉。

**建议动作**（三选一，需 Master 定）：

- (a) **分级**：`mechanism` / `number` 类必须 fetch，`attribution` 类允许 snippet。按类型卡，
  不按数量卡。工作量小，风险可控。
- (b) **比例门槛**：单篇 `snippet_only` 占比 > 50% 判 P0，否则 P1。简单但会随篇数波动。
- (c) **维持 P1**，但在发布报告与学习总结里显式列出「本篇 6/6 未 fetch」，让它可见，不做阻断。

**我的建议**：(a)。理由：`snippet_only` 的真实风险集中在机制与数字（摘要常省略条件），
归因类从摘要能判断个大概；按类型卡既提高门槛又不至于全停。

**工作量**：改 `evidence_gate.py` 判定约 1 小时，补夹具 3 条，回放验证。
**验收**：今天的卡片在 (a) 方案下应有 4 至 6 条判 P0（取决于类型标注），S1 至 S7 历史样本零误杀。

### P1-1｜`delivery_check --remote` 探活在 VPN 下必然假失败

**现象**：11-01 深夜推送成功后，`delivery_check.py --remote` 仍报
「远端探活失败，未校验（fatal: unable to access ...）」。

**证据**：直连实测 `curl -sS https://github.com` → `CONNECT tunnel failed, response 502`，
而 `git ls-remote origin` 正常返回 `cd78d38`。探活走 curl+系统代理，git 走自己的 HTTPS 栈，两条路径不同。

**根因**：`github_reachable()` 用 curl 探活。D1 的修复（探活失败不当裁判）让它不至于误判，
但也意味着 **`--remote` 的远端校验在 VPN 环境下长期失效**，等于这道检查形同虚设。

**建议动作**：探活改为 `git ls-remote --exit-code origin refs/heads/main`（走与真实推送同一通道，
探什么就验什么）。保留 curl 作为 fallback 或直接去掉。

**工作量**：20 分钟 + 改 `git_push_selftest.py` 里相关 mock 夹具。
**验收**：VPN 开启状态下 `delivery_check.py --remote` 输出「远端与本地一致: <sha>」。

### P1-3｜`score` 与 `structure_score` 双字段长期并存

**现象**：今天的 review.json 同时写 `structure_score: 100` 与 `score: 100`，`script_result` 里也是两个都有。

**根因**：C 方案要求「改名」，但 `contracts/review.schema.json` 的 `required` 里仍保留 `score`
（契约引擎不支持 `anyOf`，改动会误伤历史文件），于是落地成「两个都写、值必须相等」的过渡态。

**风险**：过渡态不会自己结束。半年后没人记得 `score` 是废弃别名，新写的消费方可能读错字段。

**建议动作**：给过渡态设一个截止日（例如 2026-12-01），到期后
`validate_review.py` 把「只写 score 不写 structure_score」从 FAIL 升级为同时要求
**删除 score**（或至少告警提示该移除）。需要先确认没有历史回放依赖 `score`。

**工作量**：确认 1 小时 + 改动 30 分钟。
**验收**：截止日后新产生的 review.json 不含 `score` 键。
