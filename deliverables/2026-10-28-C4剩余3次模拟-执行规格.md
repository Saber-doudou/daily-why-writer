## 二、为什么要专门做「含无来源 claim」的模拟

裁决书 C4 原文：

> **5 次模拟运行，不是 5 个日历日**：R3 要用 5 次模拟跑 L1 全链路（不同话题，**至少 2 次含无来源 claim**），可在 1 到 2 天内完成；真实 09:40 观察放在 R3 合并后的第一个工作日，不阻塞 R3 收口。

「无来源 claim」指的是：证据卡里某条 claim **没有可用来源**（没 url、或 `verified_by=none`、或 `confidence=unverified`），而正文却把它当事实写了。这正是证据门禁存在的意义——**它必须在 11-01 切 block 前被证明真能拦住这类输入**。前 2 次模拟（S1/S2）的 claim 全部有来源，这条防线一次都没被压过。

所以本次 3 个模拟的分工是（**下表的期望值已由验收方预先实测确认**，不是推测）：

| 编号 | 话题 | 故意造什么 | 期望门禁反应（实测值） |
|---|---|---|---|
| S3 | 为什么微波炉不能放金属？ | 一条 claim **完全没有 url**，正文照写并挂映射 | P0=2，代码 `missing_url` + `schema_invalid` |
| S4 | 为什么冰面那么滑？ | 一条 claim 有 url 但 `verified_by` 写 `"none"`、`confidence` 写 `"unverified"` | P0=2，代码 `unverified`（两个字段各触发一次） |
| S5 | 为什么鸽子走路时头一点一点？ | **完全合规**，且刻意埋三类易误杀的数字 | P0=0 |

S5 是反向对照。没有它，前两个只能证明"能拦"，证明不了"不乱拦"。

> ⚠️ 两个容易被误判成"做错了"的地方，先说在前面：
> 1. **S3 一定会同时报 `schema_invalid`**，因为证据卡 schema 里 url 是必填项。这不是重复报错，是两道防线同时生效（schema 层 + 门禁层）。看到它不要以为搞错了。
> 2. **S4 的 P0 是 2 条而不是 1 条**，因为 `verified_by: none` 与 `confidence: unverified` 各触发一次。这是当前实现的既有行为，如实记录即可。
> 3. **S3 / S4 的 P1 可能不是 0**（多为 `snippet_only`：只有搜索摘要级核实）。P1 不参与本次判定，照实填进 TSV 即可。

## 三、每次模拟怎么做（S3 举例，S4/S5 照做，只换话题和缺陷）

### 3.1 建目录

```bash
mkdir -p "F:/WorkBuddy/daily-why/eval/sim-artifacts/S3"
```

### 3.2 写证据卡 `eval/sim-artifacts/S3/card.json`

字段照 `F:/WorkBuddy/daily-why/contracts/evidence_card.schema.json`。S3 的关键是**第一条 claim 故意不带 url**：

```json
{
  "schema_version": "v1",
  "topic": "为什么微波炉不能放金属？",
  "angle": "金属反射微波产生尖端放电与电弧",
  "claims": [
    {
      "id": "C1",
      "text": "金属表面在微波场中会感应出电流，尖锐处电荷集中形成尖端放电",
      "type": "mechanism",
      "source": {
        "title": "（故意留空，制造无来源 claim）",
        "publisher": "",
        "source_level": "secondary"
      },
      "quote": "这是一段不少于十五个字的引文占位，用于满足最小长度校验",
      "verified_by": "snippet",
      "confidence": "medium",
      "counter_evidence": []
    }
  ],
  "open_questions": [],
  "banned_claims": []
}
```

注意：`source` 里**不要写 url 键**。

S4 的 defect 换一种：给出 url，但 `"verified_by": "none"` 且 `"confidence": "unverified"`。

S5 的卡要**完全合规**：有 url、`source_level: primary` 或 `secondary`、quote 不少于 15 字、`verified_by: fetch`、`confidence: high`。

### 3.3 写模拟文章 `eval/sim-artifacts/S3/article.md`

按 `daily-why-writer` 的 A+C+F 版式写，300 到 690 字，结构要有：A 段引用块、三个 `**Q1/Q2/Q3：**`、F 段 `> emoji **冷知识反转**：`、结尾 2 行 × 4 列表格（含 Markdown 分隔行）。

**关键**：正文里凡含数字的事实句，句末挂 `<!-- claim:C1 -->` 映射。S3 要把 C1 当事实写进去，这样门禁才有机会拦。

S5 要刻意埋这三处（都不能被误判）：
- 中文数字带单位，例如「上世纪五十年代」
- 表格行里出现数字，例如 「约 1/3」
- Q 标签里只有标签本身带数字，例如 `**Q1：那股风往里吹吗？**`

### 3.4 跑校验并记录真实输出

先跑文章结构校验：

```bash
"C:/Users/admin/.workbuddy/binaries/python/versions/3.13.12/python.exe" "F:/WorkBuddy/daily-why/scripts/validate_article.py" --json "F:/WorkBuddy/daily-why/eval/sim-artifacts/S3/article.md"
```

再跑证据门禁（**注意 `--mode warn`，不要用 block**）：

```bash
"C:/Users/admin/.workbuddy/binaries/python/versions/3.13.12/python.exe" "F:/WorkBuddy/daily-why/scripts/evidence_gate.py" --card "F:/WorkBuddy/daily-why/eval/sim-artifacts/S3/card.json" --article "F:/WorkBuddy/daily-why/eval/sim-artifacts/S3/article.md" --mode warn
```

门禁会在 card 同目录自动生成 `S3.gate.json`。**不要手工编辑它。**

### 3.5 记一行到 `eval/sim-runs.tsv`

列定义（8 列，Tab 分隔，顺序不能错）：

```
run_id  date  topic  s2_seconds  gate_p0  gate_p1  article_chars  note
```

- `run_id`：`S3` / `S4` / `S5`
- `date`：`2026-10-28`
- `topic`：话题文本
- `s2_seconds`：本模拟从开始到门禁跑完的墙钟秒数（可以用秒表，或 `date +%s` 前后相减）
- `gate_p0` / `gate_p1`：**必须从 `S3.gate.json` 里读**（`p0_count` / `p1_count`），不得手抄自终端印象
- `article_chars`：`validate_article --json` 输出里的 `info.char_count`
- `note`：一句话写清「造了什么缺陷 + 门禁实际报了什么代码」

### 3.6 复核没有污染生产

```bash
cd "F:/WorkBuddy/daily-why" && git status --short
```

**只应该看到 `eval/` 下的新增文件**。若出现 `articles/`、`review/`、`evidence/`、`投喂素材/` 的变动，说明做错了，立刻停下并说明。

## 六、验收方会怎么核（你可以先自查）

对照下表自检，任一条不符就算这次模拟无效：

| # | 检查项 | 判定方式 |
|---|---|---|
| 1 | S3 门禁 `p0_count=2` 且 P0 代码集合 = `{missing_url, schema_invalid}` | 读 `eval/sim-artifacts/S3/S3.gate.json` |
| 2 | S4 门禁 `p0_count=2` 且 P0 代码集合 = `{unverified}` | 读 `S4.gate.json` |
| 3 | S5 门禁 `p0_count=0` | 读 `S5.gate.json` |
| 4 | 三篇 `validate_article` 均 `passed=true` 且分数 ≥ 90 | 重跑 `--json` |
| 5 | 三篇字数均在 300 到 690 | 同上取 `info.char_count` |
| 6 | `eval/sim-runs.tsv` 新增 3 行，每行 8 列、Tab 分隔 | 读文件数 |
| 7 | TSV 里的 `gate_p0` 与 `*.gate.json` 的 `p0_count` 完全一致 | 逐行比对 |
| 8 | `git status` 只有 `eval/` 变动 | 跑 `git status --short` |
| 9 | 三个 `gate.json` 的 `mode` 字段均为 `warn` | 读文件 |

**第 7 条最容易出问题**：很多人会凭终端里看到的 P0 条数填表，而 `gate.json` 可能因为 `--mode warn` 的记录口径不同而不同。必须以文件为准。

## 七、做不到的情况怎么办

- **门禁报的 P0 代码和期望不符**：不要改文章去凑。如实记录实际代码，在 `note` 里写清差异，回报里说明。这本身就是有价值的发现（说明某条防线没按设计工作）。
- **S5 出现 P0**：说明存在误杀，这正是要测的东西。**不要为了让它变 0 而删掉那些数字**，保留原样并如实回报。
- **`validate_article` 分数低于 90**：可以按它给的 `fix_suggestions` 修文章，修完重跑，把最终结果记进去。

## 八、给执行方的最后提醒

这次要测的是**门禁能不能拦住坏输入、会不会误伤好输入**，不是写出一篇好文章。所以：

- S3 / S4 的文章质量不重要，**重要的是那个缺陷必须真实存在**并挂上了映射。
- S5 的文章必须干净，**重要的是那三类数字一个都不能少**。
- 任何一步的结果如果和期望不符，**保留现场如实回报**，比改到"看起来对"有价值得多。
