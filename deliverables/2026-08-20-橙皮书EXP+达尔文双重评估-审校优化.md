## 一、橙皮书 EXP 对照：知识非常有用，且早已预言本次优化

### 1. 最核心支撑：EXP-005 生成者与评判者分离（maker-checker）

> [根因] agent 自评会自信地夸自己；评判对象与评判者共用上下文时无法客观；自我批判难在共用一个上下文。
> [解法] 独立 evaluator：不同指令/不同模型/不同上下文；默认怀疑；完成判定交给未参与的 fresh 模型。
> [边界] 复杂任务必须双 agent（Anthropic $9 vs $200 实验：不是更贵，是不花这钱做不成）。

**对照**：daily-why 当前「主代理自审」= 完全违反 EXP-005——同一模型、同一上下文既写又审，正是「评判对象与评判者共用上下文」的反模式。隔壁 history-today 的独立 Reviewer（不加载写作规则、不同上下文、纯审核视角）正是 EXP-005 的教科书式落地。

**结论：方案 A（恢复独立 Reviewer）不只是"隔壁的做法"，而是 EXP-005 在本项目的执行。**

### 2. 路线图早已规划：EXP-015 P2 Harness 化

> [解法] 落地顺序：先 Skill 化 → 再 Harness 化（**补完成定义+验证标准+独立审核**）→ 再 Loop 化。

**对照**：橙皮书 2026-08-19 落地路线图 P2 明确写「**重要产出加独立审稿专家**」——本次审校优化正是执行 P2 欠账。橙皮书比我们还早知道该做这件事。

### 3. 诊断工具：EXP-014 校验与报告诚实性

> [根因] 单轮校验有假阴性；声称"通过"但实际有遗漏；报告的每个结论必须能在数据中找到对应字段。

**对照**：daily-why 最近 4 天 v1 全部 validate 100 分通过，但 4 篇全被 L2 揪出 P0 事实硬伤——这正是 EXP-014 警告的「单轮校验假阴性」。validate_article.py 只查格式，给的是"格式分"，却被当成了"质量分"。

### 4. 落地细节支撑

| EXP | 关键内容 | 对本次优化的支撑 |
|-----|---------|-----------------|
| EXP-004 约束优于指令 | 程序级硬拦截、熔断链是"法律"不是"建议" | 熔断链（spawn失败→去name重试→熔断→降级标注）应写死为硬约束 |
| EXP-007 Loop 五动作 | 验证=独立评判者，六零件含 Sub-agent | 验证动作必须独立，不能由生成者兼任 |
| EXP-008 触发 Skill 而非指令墙 | 审校逻辑固化 Skill，automation prompt 只留编排壳 | reviewer_prompt.md 是现成 Skill 资产，复活即可用 |
| EXP-009 六种设计模式 | ③多阶段流水线：每阶段文件产出+检查点等确认+断点恢复 | 隔壁文件检测等待（review.json 落盘+轮询）= 该模式落地 |
| EXP-012 自改进与规则治理 | 每次犯错不沉淀=同一坑反复踩 | 08-06/08-13 的失败被错误泛化为"永远不可靠"，本次纠正 |

**橙皮书对照总结**：EXP-005 给理论根基、EXP-015 给落地路线、EXP-014 给诊断方法、EXP-004/007/008/009 给工程细节——**知识完全对口，方案 A 就是橙皮书 P2 的正式执行**。

## 三、达尔文视角的优化建议（按优先级）

### P0 效果问题（最大杠杆，对应维度 7/8）
1. **恢复独立 Reviewer 为主路径**（maker-checker）——把「同步自审」从唯一路径改为「独立审校主路径 + 自审降级兜底」
2. **实测验证**：落地后 spawn 独立 agent 实测 1 次，验证能抓到自审漏检问题（对齐隔壁 08-18 实证）

### P1 结构性问题（对应维度 3/4/5/6）
3. **熔断链写死**（硬约束，EXP-004）：
   - spawn 报错 → 去掉 name 重试 1 次 → 仍失败 → 熔断（本次不再尝试）→ Orchestrator 自审 + 标注「⚠️ 未独立审校」
   - reviewer 显式上限 15 分钟（spawn 成功起算）
4. **文件检测等待**（EXP-009 流水线模式）：reviewer 结果写入 `review/{date}_review.json`，Orchestrator 每 1 分钟轮询文件是否生成，**不依赖 SendMessage**
5. **6 维度审校模板化**：把 CHECKLIST(90项)+FORBIDDEN(66条) 组织为 6 维度模板（语言/事实/叙事/术语/结构/表达），Reviewer 加载模板不加载写作规则
6. **复活 reviewer_prompt.md**：更新引用路径（validate_article.py 位置、CHECKLIST 90 项、FP 66 条），正式进入审校流程
7. **防死循环**：连续 2 轮审校指向同一 P 级问题且无实质改进 → 停止迭代，标记「⚠️ 需人工审核」

### P2 具体性问题
8. **人工检查点**：审校通过后、输出前加一处人工确认（超时自动继续，不阻塞自动化）

## 四、评估结论

1. **橙皮书知识对本次优化非常有用，且是"预言级"的对口**：EXP-005（maker-checker）是本次优化的理论根基，EXP-015 路线图 P2 早在 08-19 就规划了「重要产出加独立审稿专家」——本次正是还这笔欠账。
2. **达尔文评估确认当前自审机制严重不及格**（42.6/100 vs 隔壁 85.2/100），核心短板是违反 maker-checker 导致的事实拦截率≈0。
3. **方案 A 方向正确且被橙皮书+达尔文双重背书**，需补充 5 个工程细节（熔断链/文件检测/6 维度模板/复活 reviewer_prompt.md/防死循环），即可对齐隔壁 v9.8.2 的 85 分水平。
4. **下一步建议**：先做 spawn 可行性实验（当前会话直接 spawn 独立 agent 审 08-19 文章验证），成功即全面落地方案 A（改 SKILL.md + automation prompt + generate_prompt.py）。
