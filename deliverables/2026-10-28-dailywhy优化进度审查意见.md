## 2. 不足之处（按影响排序）

### 2.1 R3 仍是 `warn`，不是 `block`（最大缺口）

**现象**：`results.tsv` 的 R3 行写"观察期 `--mode warn`，11-01 按误杀率切 block"；10-27 的 `evidence/2026-10-27.gate.json` 也是 `mode=warn`、`blocked=false`。

**影响**：D-03 定的是"机制、数字、归因三类全阻断"，现在只是记录。10-27 的 Q1 机制句没有被门禁要求映射，靠 Reviewer 抓出 `elements_complete=False`；如果 Reviewer 漏了，门禁不会拦。**"事实漏检已解决"目前不成立，只能说"有了检测工具，还没上闸"。**

**建议**：不要无限期观察。给一个硬日期与硬前置：
- 前置 1：安全池至少 3 题升到 fetch 级；
- 前置 2：10-28 至 10-31 连续 3 篇真实文章 gate P0=0 且无新增误杀；
- 到点即切 `block`；切之前把 L1 的 `--mode warn` 改成 `--mode block`，并在发布报告里保留 gate 明细。

### 2.2 R5 金集未建，质量提升无法量化

**现象**：`eval/` 下只有 `test-prompts.json`、`historical_claims.tsv`（10 条）、`sim-runs.tsv`，没有 `eval_runner.py`，也没有 40 例金集。

**影响**：现在能证明"门禁能拦已知错误"，不能证明"事实错误率下降"。10 条历史断言 + 5 次模拟 + 1 篇实跑，是工程验收样本，不是质量基线。R6 与 R10 的停止条件原文都写"金集任一指标下降"，金集不在，这两轮的停止条件就是空的。

**建议**：R5 前移到 R4 之后、R6 之前；先做 10 例跑通，再扩到 40。用 `historical_claims.tsv` 的 10 条做种子，把 `eval_runner.py` 的事实召回、去重召回、文风胜率三项先跑出基线。

### 2.3 L2 学习总结仍未输出 JSON，R2 契约只落地了一半

**现象**：`投喂素材/20261027/` 只有 `学习总结.md`，没有 `learning_summary.json`；`l3_publish.py` 已有"JSON 优先、缺失回退正则并 warn"的分支；`daily-why-feed-learning/SKILL.md` 里没有任何 JSON 输出步骤。

**影响**：R2 的 4 个 schema 里，`review` 侧已 v1（10-27 review 带 `schema_version`），`learning_summary` 侧没有生产者。L3 仍在用正则回退，缺陷 #58 那一类"标题漂移导致改进点归零"只是被兜住，没有被消除。**P0-4 不能算完成。**

**建议**：在 L2 SKILL 的 Phase 5 增加"写 `learning_summary.json`（v1）"步骤，Markdown 只作为渲染视图；下一次 L2 必须产出 JSON，否则 R2 不结项。这是本轮最明确的一个未完成项。

### 2.4 门禁对"纯机制叙述"没有强制映射

**现象**：`check_article` 的注释写得很清楚："不能要求每句叙述都挂映射……这条受 `FACT_PAT` 限制是对的。" 10-27 的 Q1 是纯机制句，没有数字、没有 `<!-- claim -->`，门禁 P0=0；Reviewer 的 `mechanism_checks` 抓出 `elements_complete=False`。

**影响**：门禁的"机制全阻断"只在**卡片层**成立：卡片里不能有未核实的机制 claim。但**正文层**的机制转述是否忠实，门禁不管，完全依赖 Reviewer。Reviewer 漏了，机制错误就能发。这是 D-03 的一个真实覆盖缺口。R3 记录自己也列了三类盲区：机构名、人名、不带单位的中文数字，同样不触发强制映射。

**建议**：加一道独立的 `mechanism_coverage` 检查：不要求每句挂注释，但要求：
- 卡片里每条 `type=mechanism` 的 claim，正文至少被引用一次；
- 三个 Q 段各自的机制句，至少能匹配到一条机制 claim（可用关键词/句向量，先 warn）；
- 未覆盖的机制 claim 在报告里点名。
这样不制造"注释灾难"，又能把"机制有没有落地"变成可检查事实。

### 2.5 安全池证据是 snippet 级，不是 fetch 级

**现象**：`config/safe_topics.json` 的 8 题，claim 全部 `verified_by=snippet`、`confidence=medium`；R3 记录也承认"要升 fetch 级需逐页打开比对"。

**影响**：安全池是 L4 最后兜底。门禁对 snippet 只给 P1，不阻断。也就是说，**最后的兜底池本身只达到 P1 标准**。切 block 后，如果某天走到 L4，用的是一张"门禁不会拦、但也没到 fetch 级"的卡。

**建议**：切 block 前，至少把最可能用到的 3 题（建议 S02 舷窗、S03 冰面、S05 微波炉）升到 fetch 级；其余 5 题标注"P1 级兜底"，并在发布报告里保留这个标记。

### 2.6 S2 计时不是统一口径，8 分钟上限没有被严格验证

**现象**：`eval/sim-runs.tsv` 的 `s2_seconds` 为 21.1 / 26.3 / 111 / 146 / 205；重排方案自己写"S4 的 146 秒含人工思考与联网往返，和 S1 的 21.1 秒不可横向比较"；`evidence_gate.py` 里没有 `time.monotonic`。

**影响**：C5 的"8 分钟目标、12 分钟硬上限"目前是人工秒表，不是脚本计时。数字不能做 P95，也不能证明门禁不会拖垮 09:40。

**建议**：R3 补一个 `--timing` 或 R4 的 `run_metrics` 先落地，统一记录 S0 至 S6 的 `duration_ms`；在此之前，不要把 `s2_seconds` 当验收指标，只当参考。

### 2.7 台账与记录有三处版本不一致

**现象**：
- `R3-进度证据.md` 仍写"未收口""还剩 4 次模拟"；但 `C4模拟验收记录` 已写 5/5 结案，10-27 也已实跑。
- `results.tsv` 第 7 行写 `21/24 → 26/26`；当前自检是 **27/27**。
- `results.tsv` 的 `eval_mode=production_realtime`，但 10-27 是**人工实跑**，不是调度器触发；完工报告自己也承认"没有验证 09:40 调度路径"。
- `results.tsv` 没有 C4 五次模拟、#67、#68 的行；R2 记录写 77 份 review，当前是 81 份。

**影响**：审计时读者会拿到三个不同版本的事实。这不是代码问题，是**可交接性问题**：接手人无法判断哪份是最终状态。

**建议**：做一次"台账收口"：
1. 给 R3 记录加"收口补记"，指向 C4 验收与 10-27 实跑；
2. `results.tsv` 补 C4、#67、#68 三行（或合并为 R3.1/R3.2 子行）；
3. `eval_mode` 改成 `manual_production_run`，另起一行记录 09:40 调度实跑（等 10-28/10-29 真跑后）；
4. 把 26/26 改成 27/27，并注明判据修订。

### 2.8 #67 的"送达检查"还没建，R3.9 未落地

**现象**：R2/R3 的交付物在 GitHub 里缺了一整天，直到 10-27 深夜才补进白名单；`R3.9 delivery_check.py` 只在重排方案里，尚未实现。

**影响**：现在仍然可能出现"本地全绿、远端没有"。R4 至 R13 还要新增十来项资产，每一项都可能重演 #67。

**建议**：R3.9 提到 R4 之前，作为 R4 的准入条件；至少做"本轮交付物清单 → 两份白名单 → 镜像实际存在"三方核对，缺一即 exit 1。

### 2.9 阶段 0 SOP 未加载，09:40 调度路径未验证

**现象**：10-27 生产实跑是人工执行，完工报告承认"没有 Skill 工具调用""没有验证 09:40 自动触发"。

**影响**：L1 提示词写死"未完成 SOP 加载不得进入阶段 1"，这次绕过了。虽然用只读加载 + 独立审校补了证据，但流程形式上不合规；更重要的是，**自动化的真实路径没被测过**，手动成功不等于 09:40 成功。

**建议**：
- 人工实跑也必须显式加载 SOP，或在报告中给出等价的机械核对证据；
- 10-28、10-29 的 09:40 真跑必须盯，记录 automation memory、文章、review、gate 四件产物；任一缺失，先回滚再排查。

### 2.10 27/27 是修订后的判据，不是原来的 24 项全过

**现象**：`full_selfcheck` 从 24 项变 27 项；三条原恒红判据被改：素材池上限 80 取消、memory 从 ≥70 改为覆盖率 ≥90%、SKILL 的 4 处 `~` 改成"至"。

**影响**：修订本身有道理（原判据确实与文件 purpose 冲突），但"27/27"容易被读成"原来的 24 项全过了"。其中**素材池上限取消**是实质性放宽：池子从 80 上限变成无上限，现在 219 条。需要有人接住这个治理问题。

**建议**：
- 在完工报告与台账里写明"27/27 是修订后判据"；
- R12 增加一条"素材池增长治理"检查（按季度增长率、重复率、无效候选率），替代原来的硬上限；
- memory 覆盖率 36/35=103% 略高于 100%，建议核对是否有同日重复提取，或把判据改成"覆盖全部唯一日期且无重复主题"。

### 2.11 `review.schema.json` 的嵌套数组只要求 `type: object`

**现象**：`fact_checks`、`gap_checks` 等数组的 `items` 只写 `{ "type": "object" }`，一个 `fact_checks: [{}]` 也能过 schema。

**影响**：顶层字段缺失被堵住了，但嵌套内容可以是空对象。`validate_review.py` 可能补了一部分（gap_checks 7 条等），但 schema 本身比看起来弱。

**建议**：给关键数组加 `minProperties` 或至少要求 `claim`/`checked`/`verdict` 等键；或者在文档里明确"schema 只管顶层，嵌套由 `validate_review.py` 管"，避免读者误以为 schema 全包。

### 2.12 R7 后移到第 9 位，上下文压缩被推迟

**现象**：重排方案把 R7（六段拆分）从第 4 位移到第 9 位，理由是它需要 R4 的耗时数据与 R5 的回归能力。

**影响**：R7 是解决"提示词 82.5K 字符、120:1"的主要结构手段。后移有依赖依据，但意味着**最初四大痛点里的"上下文太长"要更晚才动**。R6（规则分层）在第 4 位，能缓解一部分，但不是结构性的。

**建议**：接受后移，但给一个明确期限（例如 R6 完成后 2 周内必须启动 R7），并在 R6 后测一次 Writer/Reviewer 的实际字符数，决定 R7 是否还需要按原方案做六段。
