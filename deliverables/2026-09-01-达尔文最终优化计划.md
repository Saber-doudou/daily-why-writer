## 0. 计划定位：把「Karpathy Loop」适配到 Daily Why 三技能

autoresearch 三要素 → 本项目的对应物：

| Karpathy 三要素 | Daily Why 对应 | 现状 | 缺口 |
|---|---|---|---|
| **单一可编辑资产**（train.py） | 4 个 SKILL.md + 配套脚本 | 已具备 | 版本号跨文件脱节（P1-7），缺单一权威源 |
| **单一客观指标**（val_bpb） | 达尔文 8 维加权总分 | 已具备 rubric | **缺基线**：4 个 skill 从未做过 8 维评估 |
| **固定时间预算**（5 分钟/实验） | 每轮优化 = 1 次技能修改 + 1 次验证 | 未定义 | 需在计划中固化每轮预算与轮次上限 |

**本项目与 autoresearch 的关键差异**（尊重达尔文约束）：
1. 验证不能完全自动 —— 文章质量需独立 Reviewer 判断，采用 **dry_run + 真实运行数据**双轨（今日审计已提供大量真实运行证据，优于纯 dry_run）；
2. 人是最终裁判 —— 每个 skill 优化完暂停等 Master 确认（Human-on-the-Loop，非 Human-in-the-Loop）；
3. 棘轮 —— 只保留分数严格提升的改动，否则 git revert。

## 1. 外部经验吸收（本次检索 3 条关键经验）

### 经验 A：Niklaus「Don't Train the Model, Evolve the Harness」（Hugging Face，2026）
- 同模型、仅优化外层执行机制：pooled score **3.5% → 80.1%**，22 轮自动迭代；
- 关键结论：**最大的性能改进往往来自「文件处理等自动化步骤」，而非消耗大量 Token 修改提示词**；
- 反面教训：模型推理全对但**存错文件名 → 0 分** —— 对应本项目「发布报告被手工改动」「review 分数与产物不匹配」是同类 Harness 级错误。
- **落地映射**：本次优化的主战场应放在 **脚本层（l3_publish.py / generate_prompt.py / validate_article.py）**，而非继续堆 prompt 文字。

### 经验 B：Anthropic Skills「Evaluation-driven development」+「Claude A/B 测试」
- 流程：识别缺口 → **先建 3 个测试场景** → 建立 baseline → 最小指令 → 迭代 → 评估是唯一真源；
- Claude A（设计优化）与 Claude B（执行验证）分离 —— 即 EXP-005 maker-checker 的官方形态；
- Enterprise 要求：每个 Skill 配 **3 到 5 个代表性评估查询**（应触发 / 不应触发 / 模糊边界）+ 作者不能自审 + 版本 pin + checksum 校验。
- **落地映射**：为 4 个 skill 建立 `test-prompts.json`（§4）；发布脚本加 checksum 校验（对应 P1-3 prompt 错字）。

### 经验 C：双层 autoresearch「外层循环打破思维定势」
- 内层循环优化产物，**外层循环强制探索模型本能回避的方向** → 性能比基准提升 5 倍；
- 对应本项目**审校盲区**（P1-A4 / FP-67）：Reviewer 只验证可搜索的事实断言、回避机制自洽性 —— 需在 Reviewer prompt 中强制加入「机制方向自洽」这一 Reviewer 本能回避的维度。
- Codila 四要素适用性判断（Daily Why 是否值得 Loop 化）：任务高频 ✅（每工作日）/ 验证可自动化 ⚠️（部分，validate 脚本可自动化，质量需 Reviewer）/ Token 预算 ✅ / 真实运行环境 ✅ → **值得，但验证环节保留人工检查点**。

## 6. 棘轮机制与回滚（EXP-012 + darwin 约束）

1. **只保留改进**：每步改动后重新评估（结构主 agent 自评 + 效果用独立子 agent 或真实运行），新总分 **严格高于** 旧总分才 keep；
2. **git 分支隔离**：全部改动在 `auto-optimize/` 分支，回滚用 `git revert`（禁用 reset --hard）；
3. **results.tsv 记录**：每轮每步追加一行（timestamp / commit / skill / old_score / new_score / status / dimension / note / eval_mode）；
4. **每 skill 轮次上限 3 轮**，round 1 即涨不动 → 提议「探索性重写」（需 Master 同意）或跳过；
5. **人类检查点**：每 skill 优化完 → 展示 git diff + 分数变化 + 测试输出 → Master 确认「OK」才继续；
6. **每轮只改一个维度**：避免多变更无法归因（darwin 约束 3）。

## 8. 风险与边界

| 风险 | 缓解 |
|---|---|
| 脚本改动引入回归（P1/P2 改 git 流程） | 每步后跑测试集 4.1 全 3 场景；改动只在分支，可 revert |
| Reviewer prompt 加维度后过度严格、误伤正常文章 | W1 写「例举反例 + 判级标准」，先跑 3 篇历史文章回归 |
