# Daily Why 去重机制复盘与重构方案（2026-09-09）

> 背景：9月8日 L1 自动化产出《蜂蜜能放几千年都不坏》，与 8月4日《蜂蜜放再久也不坏》为同一选题重复。Master 直觉正确。
> 本文回答三个问题：① 以前和现在去重机制是否一样；② 是否必然暴雷；③ 更切实的修复思路（含业界经验与橙皮书参考）。

---

## 一、以前 vs 现在：去重机制演化（本地代码考古）

结论：**不一样，且现在比历史上的任何版本都更弱。**

| 时期 | 去重实现 | 性质 | AI 能否跳过 |
|---|---|---|---|
| 早期（模板选题时代）`archive/auto_generate.py`、`scripts/send_daily_why.py` | `select_new_theme()` 内联**硬循环**：`for _ in range(20): if theme not in history_themes: break` | 代码强制，从 `memory.md` 读最近30条历史主题做精确匹配 | **不能**（是代码逻辑，不是提示） |
| 现在（AI 自由选题时代）`automation-prompt-latest.txt` 步骤3 | prompt 里写"请对每个候选运行 `check_topic.py --angle`" | **纯 AI 软约束** | **能**（AI 可不调用、可忽略结果） |

关键事实：
- 当前 `scripts/send_daily_why.py` 第48至85行**仍残留**那套代码硬去重（`load_history_themes` + `select_new_theme` 循环20次），但它是为"模板随机选题"设计的**死代码**——现架构是 AI 自由选题，根本不调它。这给人"我们有去重"的错觉，实则已脱节。
- `check_topic.py` 本身正确（实测能从 `topics_context.json` 检出8月那篇，相似度71%判重复），但生产流程里**没有任何代码级调用**：`l3_publish.py` 只把它列进"需同步文件清单"，`full_selfcheck.py` 只把它当测试用例。真正驱动它的是 prompt 文本。

## 二、是否必然暴雷？—— 是，且概率高于旧版

- 旧版至少有"代码硬循环"兜底，AI 跑出题外也会被循环挡住。现在连这层兜底都丢了，**完全依赖 AI 自觉调用 `check_topic.py`**。
- `--angle` 模式在相似度 50%至70% 区间会**主动放行**（只提示"角度相关"），进一步放大风险——同主题稍换措辞极易跌入该区间被放过。
- 这是结构性必然，不是偶发。本次9月8日就是 AI 选题时未真正执行去重，重复话题直接落盘并发布。

## 三、业界经验与橙皮书参考（均指向同一结论）

### 1. 真实生产事故（最直接佐证）
- **vaylostudios — "Your Autonomous AI Agent Will Spam Itself"**
  https://vaylostudios.com/blog/autonomous-ai-agent-idempotency-fix
  > "The obvious first move is to just tell the agent, in its system prompt, to check for existing tasks... Prompt instructions are advisory. Under enough repetition, the model skips the check... A production audit cron built exactly this way ended up creating dozens of duplicate tasks."
  > **正解**："Move the check out of the prompt and into the tool itself."（把检查移出 prompt，移进工具本身）
  > **关键细节**：去重守卫**只应针对自动化调用者**；人类刻意创建相似项不该被硬拦，否则只是碍事。

- **dev.to/tarunai — "My AI Agent Hit a Duplicate Post Error"**（LinkedIn 重复发布事故）
  https://dev.to/tarunai/my-ai-agent-hit-a-duplicate-post-error-here-is-the-engineering-lesson-dm2
  > "the content engine was treating logs as a reporting layer instead of a generation constraint. That is backwards. Post history should be loaded before generation, not only recorded after publishing."
  > 实用守卫只需 `SequenceMatcher` 相似度 ≥0.82 起步，不必一上来就上 embedding。

- **tianpan.co — "Idempotency Is Not Optional in LLM Pipelines"**
  https://tianpan.co/blog/2026/04/20/idempotency-llm-pipelines
  > 语义去重漏斗：快字符串匹配 → embedding 相似度（阈值0.85至0.9）→ LLM 验证（仅边界）。分离 ingestion 与 processing，去重发生在队列层而非 handler 层。

### 2. 橙皮书（花叔《Agent Skills 橙皮书》）
GitHub: https://github.com/alchaincyf/agent-skills-orange-book
> 第一章核心论点："AI 不记得，每次新对话是一张白纸。Agent Skills 解决的就是这个问题——把工作流程、判断标准、写作规范封装进 SKILL.md，AI 在对应场景自动加载。"
> 其"多阶段流水线型"设计模式，正是把流程拆成阶段、每阶段设**硬检查点**的思路。

**与本案的咬合**：当前去重依赖 prompt 软提醒，正是橙皮书点名的"AI 失忆式跳过"。正确做法=把去重固化成**自动加载的工具/检查点**，而非每次 prompt 里说一遍。

### 3. 共识提炼
| 共识 | 来源 |
|---|---|
| prompt 软约束不可靠，必须移进工具/代码硬卡点 | vaylostudios、EXP-004 |
| 守卫只针对自动化路径，人类手动不硬拦 | vaylostudios |
| 历史应在生成前加载为约束，而非发布后记录 | dev.to/tarunai |
| 简单 string similarity 起步即可，不必先上 embedding | dev.to/tarunai |
| 漏斗式分层（字符串→embedding→LLM） | tianpan.co |

## 四、更切实的重构方案（三层 + 人机区分）

不是简单"加硬卡点阻断"，而是分层且区分调用者：

### 层1：硬卡点（代码层，仅自动化路径）
- 在 **`l3_publish.py` Phase 0 之前**加 dedup gate：对待发布的当日文章，subprocess 调用 `check_topic.py` **严格模式（不带 --angle）**，退出码1 → 拒绝发布并输出"选题重复，已拦截"。
- 这是最关键的**对外防线**：即使 L1 写了重复文章，`l3_publish` 发布前必拦，避免对读者重复。
- 加 `--allow-human-override` 开关 / 环境变量：当 Master **手动**触发写作时，守卫放行（不硬卡死人类意图）。自动化路径默认开启硬拦截。

### 层2：生成前加载约束（数据层）
- 确保 L1 选题前必跑 `prepare_topics.py --compact` 刷新 `topics_context.json`。
- 选题时把"最近 N 条已用话题"作为**硬上下文**注入 AI 工作区，而非"发布后才记"（呼应 dev.to/tarunai：历史是生成约束，不是报告层）。

### 层3：可观测（日志层，呼应铁律 EXP-014）
- L1/L3 流程强制记录 `check_topic` 的退出码与输出，使"未去重"在日志可审计，而不是事后翻文章才发现。

### 附：死代码清理
- `scripts/send_daily_why.py` 第48至85行的旧硬去重是死代码（为模板选题设计，现不调用）。要么改造复用（用作层1的本地兜底），要么删除，避免"以为有去重"的错觉（符合铁律"死文件判据"）。

## 五、行动建议
1. 先落**层1**（l3_publish 发布前 dedup gate + 严格模式 + 人机开关）——止血最快，且纯代码、不影响现有 AI 选题流程。
2. 再补**层3**日志，使去重可观测。
3. 最后做**层2**与死代码清理，把去重从"AI 自觉"彻底变为"工具固化"。

> 该缺陷应记入缺陷台账（defects.md）：本质是铁律 EXP-004 的反面教材——"改 prompt 不加机械校验 = 无效"。

## 六、实施记录（2026-09-09 已完成）

在 `scripts/l3_publish.py` 落地**层1 硬卡点**（Phase 0 话题去重 gate），遵循"不影响流程运转"原则：

- 新增 `dedup_gate_check(articles, res)`：扫描当日初版/优化版，读首行去 emoji 提取话题，subprocess 调用 `check_topic.py` 严格模式（**不带 --angle**）。
- 设计要点（呼应铁律 EXP-004 / EXP-014）：
  1. **fail-open**：check_topic 异常/超时/缺失/参数错 → 放行 + warn，**绝不拖垮发布流程**。
  2. **人机区分 + 三态开关**：
     - 默认（无环境变量）：软告警（warn 不阻断）——**已上线，不影响现有发布**。
     - `DAILY_WHY_DEDUP_ENFORCE=1`：硬拦截（res.fail + sys.exit，发布中止）——止血模式，建议观察期后开启。
     - `DAILY_WHY_DEDUP_OFF=1`：紧急总开关，整体关闭。
  3. 兼容无 `#` 标题的新文章格式（读首行去 emoji 提取话题）。

**验证（均用 --dry-run 隔离副作用）：**
- 默认模式跑 9月8日蜂蜜文章 → 正确命中重复（相似度71%）→ 软告警，流程完整跑通 Exit 0 ✅
- `DAILY_WHY_DEDUP_OFF=1` → gate 跳过，流程正常 ✅
- `DAILY_WHY_DEDUP_ENFORCE=1` → 硬拦截，发布在 Phase 0 中止（2 错误）✅

**后续（2026-09-08 已执行「直接来硬的」）**：`DAILY_WHY_DEDUP_ENFORCE=1` 已注入 L3 自动化实际调用——`C:/Users/admin/.workbuddy/skills/daily-why-publish/SKILL.md` 的 Step 1 预检（`--dry-run`）与 Step 3 发布命令均加前缀 `DAILY_WHY_DEDUP_ENFORCE=1`，使 L3 自动化触发即硬拦截（不再是 AI 可跳过的软提示，落实 EXP-004）。版本号三处对齐升至 v3.13（l3_publish.py / SKILL.md frontmatter+footer+changelog / config/version.json）。端到端验证：对 9月8日蜂蜜文章跑 `DAILY_WHY_DEDUP_ENFORCE=1 ... --dry-run`，v1+v2 均被 exit 1 硬拦（相似度71% 命中8月蜂蜜）。层2（生成前加载历史约束）按 Master 设计警示不做全量历史加载（见缺陷台账 #44：增成本/污染上下文/误导 AI 以为是挑选池）；send_daily_why.py 死代码已于 2026-09-09 核实并删除，缺陷台账补记 #43（蜂蜜重复=EXP-004 反面教材）/#44。
