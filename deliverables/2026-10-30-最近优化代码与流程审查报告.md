## 2. 🔴 P0-1　11-01 切 block 的兜底路径未接线

`scripts/generate_prompt.py` 第 287 行白纸黑字写着：

但对全文件 grep「删 claim / 定向补证 / 换角度 / 安全池 / 兜底」，命中只有：

| 行号 | 性质 |
|---|---|
| 211 / 275 / 280 | **选题去重**的兜底（外部源 → 脑洞 → 素材池），与证据门禁无关 |
| 287 | 切 block 的**未来时说明**，不是可执行步骤 |
| 321 | 审校 spawn 熔断链，与门禁无关 |

**L1 全流程没有任何一步告诉 AI：门禁返回 exit 1 之后该做什么。**

### 为什么这是 P0

- `evidence_gate.py` 第 598 行：`if p0 and args.mode == "block": return 1` —— 切 block 后**真的会阻断**。
- 但阻断之后没有第 4 级兜底可走，AI 只能在「硬着头皮发」「卡死」「自由发挥」之间随机选一个。
- 这正是铁律 **EXP-004「约束优于指令」** 的反例：阻断是机械的（代码保证），
  兜底是指令性的（而且压根没写成指令）。约束强的一侧生效、弱的一侧不存在，结果是**卡死**。

### 附带发现：样本被高估 1 天

CHANGELOG v5.7 写「10-30/10-31 两天真跑还可积累误杀样本」。但 **10-31 是周六**，
L1 自动化仅工作日 09:40 触发 → 10-31 样本**不可能拿到**。实际误杀样本止于 4 个（10-27 至 10-30）。

### 建议

切 block 前必须先把兜底写成**可执行步骤**（不是说明句），至少补：
exit 1 → ① 删该 claim 重跑 → ② 定向补证 → ③ 换角度 → ④ `safe_pool.py --consume` 取安全题，
并明确「四级皆失败才允许上报失败」。

## 7. 🟡 P1-4　门禁判据的误杀面（切 block 后会放大成阻断）

### 7.1 `FACT_PAT` 裸字符匹配（evidence_gate.py 第 36 行）

```python
FACT_PAT = re.compile(
    r"\d|倍|百分之|[一二三四五六七八九十百千万]+分之[一二三四五六七八九十]+"
    r"|[一二三四五六七八九十百千万]+(?:年|倍|米|毫米|厘米|吨|公斤|克|摄氏度|度|分钟|小时)"
)
```

- `倍` 与 **`度`** 是**裸字符**：「态度」「角度」「程度」「过度」「知名度」「倍感」全部命中。
- `\d` 裸匹配：任何含阿拉伯数字的句子（含年份、编号）都算事实句。

现有豁免只有两条：表格行（`body.startswith("|")`）、Q 标签（`^\*{0,2}\s*Q\d+\s*[：:]`）。
**「度」字的豁免完全没有。**

4 天实测 P0=0 只说明样本恰好没触发，**不等于判据安全**。切 block 后任一命中即 P0 阻断。

### 7.2 `banned_claims` 子串匹配（第 102 行）

```python
if b and b in text:
```

短字符串会大量误命中（如 banned 写「银能解毒」，正文出现「银能解毒吗」也命中）。
切 block 后即 P0 误杀。

### 建议

切 block 前：① 给 `度` 加否定式上下文（排除「态度/角度/程度/过度/知名度」等）；
② `banned_claims` 改**规范化后全等或最小长度门槛**（如 ≥8 字才启用子串匹配）。

### 决策 1　11-01 到底切不切 block？

**现状**：观察期 10-27 至 10-30（4 个工作日）实测 P0=0/P1=0，但兜底未接线、block 路径零测试。

**外部经验（风控 / DDoS 规则上线的成熟做法）**：

> 规则应遵循「**先观察、后告警、再拦截**」的灰度流程。
> 第一阶段旁路观察**只记录不阻断，持续至少 72 小时**，统计命中中合法流量占比，
> **若合法流量占比超过 5%，说明规则存在明显误杀风险**；
> 第二阶段告警模式，持续 3 至 7 天；第三阶段才小范围拦截（先 1% 至 5%）。
> **全量上线后仍需保留实时监控和自动熔断机制**——当误拦导致业务指标异常达到阈值时，
> 系统**自动将规则降级回观察模式**。
> —— DDoS/CC 防护规则灰度实践（jcwlyf.com/content-59188.html、/content-59766.html）

另有 kill switch 原则（Martin Fowler 分类，经 Safeguard / KodeKloud 转述）：

> **如果需要一次新发布才能把它关掉，那这个开关就已经失职了。**
> 关闭必须快于发布；kill switch 应能从**不依赖开关服务**的本地配置读取。
> —— safeguard.sh/resources/blog/kill-switch-vs-feature-flag-vs-rollback

**对照本项目**：

| 灰度阶段 | 行业要求 | 本项目实际 | 判定 |
|---|---|---|---|
| ① 旁路观察 ≥72h | 只记录不阻断 | 10-27 至 10-30，4 个工作日 P0=0 | ✅ 已满足 |
| ② 告警模式 3 至 7 天 | 打标记 + 通知，仍不阻断 | **无此阶段** | ❌ 缺失 |
| ③ 小范围拦截 1% 至 5% | 先看局部再放量 | **直接 100% 全量 block** | ❌ 缺失 |
| ④ 自动熔断回退 | 误杀超阈值自动降级 | **无任何回退机制** | ❌ 缺失 |

**🔵 推荐：切，但改成两阶段 + 先装 kill switch**

1. **先装 kill switch（必须，半天工作量）**：给 `evidence_gate.py` 加环境变量级开关
   `DAILY_WHY_GATE_RELAX=1`（命中即降级为 warn，不阻断）。
   项目里已有同型先例 `DAILY_WHY_DEDUP_RELAX=1`，模式一致、零学习成本。
   *理由*：现行 `--mode` 写在 automation prompt 里，改它要改 prompt → `--update-automation`
   → 写库 → **次日才生效**。按 Fowler 的标准，这等于「关掉它需要一次发布」= 开关失职。
   装了环境变量开关，出事可**当次立刻降级**。
2. **11-01 只切「高置信子集」**：先只让 `tertiary_only`、`banned_claim_hit`、`unknown_claim`
   三类转 block（这三类判据确定、误杀面窄），`unmapped_fact` / `unverified_mapping`
   **继续 warn**（这两类依赖 FACT_PAT 与映射，误杀面宽，见决策 4）。
   观察 1 至 2 个工作日无异常，再全量切。
3. **定回退阈值并写成规则**：连续 2 个工作日出现 P0 阻断，或单日 P0 ≥ 2 → 自动降级回 warn 并告警。

**若 Master 选择「推迟」**：也建议至少先装 kill switch——它是唯一能在出事时救场的东西，
且与切不切 block 无关，独立有价值。

### 决策 2　是否转 C 方案（Reviewer 降级为形式门禁）？

**现状**：漏判率 6/6 = 100%；v1 对含 4 处 P0 硬伤的初稿判 `score=100 / issues=0`。
Master 09-07 已预先裁定触发条件，但从未执行。

**外部经验（LLM-as-judge 的可靠性剖面）**——这份材料直接给出了「什么能交给 AI 判、什么不能」：

| 评估形态 | 可靠性 | 成本 |
|---|---|---|
| **确定性校验（schema / 正则 / 必填字段）** | **高** | 极低 |
| 二元 pass/fail（紧 rubric） | 中高 | 中 |
| 成对比较（A vs B 哪个更好） | 中高 | 中 |
| **LLM 连续打分（0 至 100 开放式质量分）** | **低至中** | 中高 |
| 人工复核 | 最高（权威） | 高 |

> **凡是规则能解决的，就用规则**（schema 校验、正则、存在性检查——更快、更便宜、更可靠）。
> 把 LLM 留给剩下的部分。
> 最常见的错误不是选错行，而是**在本该用确定性校验或成对比较的地方，用了 LLM 连续打分**；
> 评审之所以被部署，是因为它「感觉很全面」，它能活下来，是因为**没人测量过它是否还诚实**。
> —— flowverify.co/blog/llm-judge-production-failures

另有校准准则：

> 把校准变成**策略**而非一个可以庆祝的分数：
> 仅当确定性检查通过、案例在已校准域内、评审给出有效证据且未弃权、反事实顺序检验无分歧时
> 才自动接受；**其余一律路由给人**。
> —— stanleycyang.com/writing/calibrate-llm-as-a-judge

**对照本项目**：v1 Reviewer 现在干的两件事，恰好落在**可靠性最低**的两格——
① 开放式 6 维度连续打分（score=100）② 事实/机制判断（需外部核验的开放域）。
而它**本可以**干的是可靠性格：结构完整性、字数、FORBIDDEN 命中、schema 合规。

**🔵 推荐：转 C 方案，且今天就转**

- Reviewer 正式降级为**形式门禁**：只验 schema / 字数 / FORBIDDEN / 结构 / 必填数组。
- 事实与机制责任**明确划归 L2**（本来就是 L2 四 AI 在兜，10-30 实测又一次证明：
  6 条差距全靠 L2 抓，Reviewer 零贡献）。
- 停用 review.json 里的 `score` 字段（或改名 `structure_score` 并注明「不含事实判断」），
  **杜绝 100 分被误读为「内容没问题」**——这是本次最实际的止血点。
- 依据 Master 09-07 既有裁定，触发条件早已满足，无需再等。

**代价**：失去一道名义上的独立复核。但 100% 漏判 + 主动发绿灯的复核，
比没有更危险——它会让下游**降低警惕**。诚实承认它没有，反而更安全。

### 决策 3　版本号撞号怎么修？

**现状**：SKILL 变更日志表第 341 行已有 `| v3.3 | 2026-08-17 |`（实为 v3.0.3），
与 10-30 新进位的 v3.3（实为 v3.3.0）字符串全等；字符串比较 `"v3.3" < "v3.28"` 会误判新旧。

**外部经验（SemVer 2.0.0 权威规范）**——规范里有一条**几乎是为本项目写的警告**：

> 标准版本号**必须**采用 X.Y.Z 格式，其中 X、Y、Z 为非负整数，**且不得包含前导零**。
> …… 主版本号、次版本号、修订号**必须以数值方式比较**。
> **一旦某个数字段超过 9，用字符串比较而非 semver 优先级排序的工具，会静默排错任何版本。**
> —— semver.org（中文版 semver.org/lang/zh-CN/）

规范还明确：**版本号的三个段一个都不能省**。本项目「省略第二个点」的两位写法（v3.3）
本身就**不符合 SemVer**——它既可读作 v3.3.x 也可读作 v3.0.3，歧义是规范层面就禁止的。

**🔵 推荐：新版本写作 `v3.3.0`（完整三段式）**

- 彻底消除与 08-17 老 v3.3 的撞号（老的可回注为 `v3.0.3`，但**不改历史引用**，只在新条目注明）。
- 符合 SemVer，任何 semver 库都能正确排序（`v3.3.0 > v3.2.8` 数值比较成立）。
- 与 Master 既定的三段式铁律一致，只是**把省略的那个点补回来**。
- 顺带：在 341 行老条目加注「(=v3.0.3，08-17)」，避免日后考古踩坑。

**备选（不推荐）**：保持 v3.3 两位写法。代价是字符串排序永远有坑，
且任何未来引入的 semver 工具都会误判。

### 决策 4　FACT_PAT 误杀面怎么收窄？

**现状**：`度` / `倍` 为裸字符（态度、角度、程度、过度全命中），`\d` 裸匹配；
`banned_claims` 用 `b in text` 子串匹配。4 天 P0=0 只说明样本没触发。

**外部经验**：上面决策 1 引的灰度原则里有一条可直接量化：
**「命中请求中合法流量占比超过 5%，说明规则存在明显误杀风险，需调整条件或阈值」**。
本项目 4 天样本里 `unmapped_fact` 命中数为 0，**根本无法估出这个占比**——
样本量太小，这正是决策 1 建议「先切高置信子集」的直接理由。

**🔵 推荐：先窄后宽，分三步**

1. **给 `度` 加否定式上下文**：排除「态度 / 角度 / 程度 / 过度 / 知名度 / 温度」以外的裸「度」，
   实际改为要求「数字 + 度」或「摄氏 / 度」组合，而非裸字。
   `倍` 同理要求前置数字（「三倍」「1.5 倍」命中，裸「倍感」不命中）。
2. **`banned_claims` 加最小长度门槛**：≥8 字才启用子串匹配，短串改全等匹配。
3. **补反向夹具**：造「态度 / 角度 / 程度」三句进 `SELFTEST`，锁死「一修就松」——
   这与项目既有的 F1/F2 互为反向夹具做法是同一手法，直接照搬即可。

**顺序建议**：先做 3（夹具），再做 1、2。夹具先行的好处是修完立刻能证明「真的没回归」。
