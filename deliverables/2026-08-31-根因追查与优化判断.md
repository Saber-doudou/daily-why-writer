## 1. L3 Phase 顺序：为什么归档排在 git 之后

### 1.1 你问的问题，答案是「原始设计没错，错在后来的一次修补」

我原以为是设计者疏忽。查完 git 历史，结论相反：**设计是干净的，是 08-28 的一次修补打破了这个干净。**

### 1.2 时间线（全部有提交哈希）

| 日期 | 提交 | 变更 | 当时是否自洽 |
|---|---|---|---|
| 2026-06-22 | `fd1dedb` | L3 首版，Phase 0 到 4：参数解析 / 匹配度检查 / IMA 备份 / GitHub 推送 / 记忆归档。**无 Phase 5** | ✅ |
| 2026-06-26 | `9e236a7` | **新增 Phase 5**（FEEDBACK 休眠归档），追加在 `main()` 末尾 | ✅ 见 1.3 |
| 2026-08-28 | `5c5ef5a` | B 组补全：把 `FEEDBACK_ARCHIVE.md` 加进 `git_add_files` + `files_to_copy` | ❌ **打破自洽** |

### 1.3 关键证据：06-26 时归档产物根本不进版本库

`git show 9e236a7:scripts/config.json` 的 `git_add_files`（06-26 当时版本）：

```json
"git_add_files": [
  "SKILL.md",
  "references/FORBIDDEN.md",
  "references/CHECKLIST.md",
  "references/FEEDBACK_LOG.md",
  "scripts/l3_publish.py",
  "scripts/config.json",
  "daily-why-publish/SKILL.md"
]
```

**没有 `FEEDBACK_ARCHIVE.md`。**

而 `archive_lessons.py` 会写两个文件：
- `FEEDBACK_LOG.md` ← 在清单里 ✅
- `FEEDBACK_ARCHIVE.md` ← **不在清单里** ❌

所以 06-26 的设计意图很清楚：**休眠归档的产物是本地存档，不进版本库**。既然不进 git，那 Phase 5 排在 Phase 3 之后就毫无冲突——设计者把 Phase 5 当作「发布完成后的收尾清理」，这个定位是合理的。

`docs/自动化流程全面优化计划-20260813.md` 第 36 行也印证了这个定位：
```
[人工/触发] → L3 发布（预检 → IMA 备份 → GitHub 推送 → 归档）
```
「归档」明确写在发布链路之后。

### 1.4 08-28 那次修补做了什么、漏了什么

08-28 审计发现 `FEEDBACK_ARCHIVE.md` 源 189 行 vs repo 35 行脱节，于是补进同步清单。补得对不对？**对**——35 行说明它曾经同步过，是后来脱节的，属于真问题。

但这次修补**只补了数据面（复制源），没补控制面（执行时序）**：

```
FEEDBACK_ARCHIVE.md 的性质变了：
  本地存档  ──08-28──▶  需进版本库的同步文件

  而生产它的 Phase 5 仍在 Phase 3（git）之后
  → 每日新增归档永久滞后一个提交
```

08-31 实证：commit 11:58:45，归档 11:59:06，差 21 秒，repo 189 行 vs 源 197 行。

### 1.5 真正的规律（这才是要写进 SOP 的东西）

不该表述为「归档要在 git 之前」——这是个案结论，下次换个文件照样踩坑。

**正确的约束是：**

> **任何 Phase，只要它的产出物出现在 `config.json` 的 `git_add_files` 里，该 Phase 就必须在 Phase 3（git commit）之前执行。**

这是一条**数据流依赖约束**，不是某个 Phase 的特殊要求。08-28 的疏漏本质是：把文件加进同步清单时，没有回头检查「谁在生产这个文件」。

### 1.6 修法对比与我的判断

| 方案 | 做法 | 优点 | 缺点 | 我的评价 |
|---|---|---|---|---|
| **A. 前移 Phase 5** | 顺序改为 0→1→2(IMA)→**5(归档)**→3(git)→4(记忆) | 一次根除；符合「生产先于提交」的直观逻辑 | Phase 编号不再按执行顺序单调（日志里会看到 2→5→3）；归档脚本报错会挡在 git 前面 | **推荐** |
| B. 归档后二次提交 | Phase 5 后检测 diff，有则补提一个 commit | 主链路零风险，归档失败不影响发布 | 每天可能 2 个 commit；「补提」逻辑本身也要维护 | 备选 |
| C. 移出同步清单 | 把 FEEDBACK_ARCHIVE.md 从 `git_add_files` 删除，恢复 06-26 设计 | 零代码改动，立刻回归自洽 | 丢失休眠教训的版本历史；若 skill 目录损坏则不可恢复 | 不推荐 |

**推荐 A，理由：**

1. FEEDBACK_ARCHIVE 是**规则库资产**（已归档的教训，未来可能被重新激活），进版本库是对的，08-28 的判断没错。既然判断没错，就该让时序去适配它，而不是反过来牺牲它。
2. 选 `0→1→2→5→3→4` 而非 `0→1→5→2→3→4`：改动最小（只把 5 从末尾挪到 3 之前），且 IMA 备份的是 MEMORY.md、与归档无关，两者顺序不影响结果。
3. **必须加的保护**：Phase 5 内部失败时走 `res.warn` 而非 `res.fail`，不得阻塞后续 IMA/git。归档是维护性动作，不该有阻断发布主链路的权力。

**同时建议在 `l3_publish.py` 内置一条自检**（与已有的 `git_add_files` 复制源自检并列）：扫描所有会写文件的 Phase，若其产出物命中 `git_add_files` 但该 Phase 序号 > 3，则启动即告警。把 1.5 的规律固化成代码。

## 2. 得分记错：不是算错，是表格被降级了

### 2.1 先看事实：7 次里 5 次对不上

我跑了全部历史 review.json 的实测值，和仪表盘记录对照：

| 日期 | review.json 实际 score | 仪表盘记录 | 是否一致 |
|---|---|---|---|
| 08-21 | 100（p2=4） | ✅100 | ✅ |
| 08-24 | **96**（p2=5） | ✅100 | ❌ |
| 08-25 | 100（p2=0） | ✅100 | ✅ |
| 08-26 | **96**（p2=2） | ✅100 | ❌ |
| 08-27 | **92**（p1=1, p2=5） | ✅100 | ❌ |
| 08-28 | **93**（p2=4） | ✅100→95 | ❌ 两个数都不对 |
| 08-31 | **93**（p2=2） | ✅100 | ❌ |

**7 次里 5 次不符**——这是系统性现象，不是今天的偶发失误。

### 2.2 根因：表头从 6 列被砍成 4 列

L2 SOP（`daily-why-feed-learning/SKILL.md` 第 401 行）规定的模板是：

```markdown
| 日期 | 话题 | AI数 | 新FP | v1分→v2分 | 状态 |
|------|------|------|------|-----------|------|
```

**6 列，明确区分 v1 分与 v2 分。**

而 08-27 的备份 `MEMORY.backup.20260827.md` 里，表是完整正确的：

```
| 2026-08-26 | 蛇没脚爬行 | 4 | ... | 100→100 | ✅ |
| 2026-08-25 | 保鲜膜贴碗口 | 4 | ... | 100→100 | ✅ |
| 2026-08-24 | 左右鼻孔轮班 | 4 | ... | 96→100  | ✅ |   ← v1=96，与 review.json 完全吻合
```

**08-24 那行的 v1 分是 96，和 review.json 的 96 一模一样。** 说明原始表格是准的。

现在的 MEMORY.md 表头：

```
| 日期 | 话题 | 新规则 | 状态 |
| 08-24 | 左右鼻孔轮班 | §96/97/98 | ✅100 |   ← 96→100 被压成 100
```

**4 列。AI数、新FP、v1分→v2分 三列全部消失**（日期格式也从 `2026-08-26` 缩成 `08-26`）。

列没了，`v1→v2` 两个数无处安放，执行者就：
- 要么塞进「状态」列（08-28 写成 `✅100→95`，两个数都不对）
- 要么只填一个数（选 v2 的 100）

**v1 的审校分就此永久丢失。**

### 2.3 更深一层：v1 和 v2 的分数本来就不可比

即使表头恢复，`v1分→v2分` 这个设计本身也埋着问题：

| | v1（初稿） | v2（优化版） |
|---|---|---|
| 谁评的 | **独立 Reviewer**（人工 + 脚本，含事实核验） | **只有 validate_article.py 脚本** |
| 分怎么来的 | 综合分，人工扣分 | 纯结构检查，12 项全过即 100 |
| 08-31 实际 | 93 | 100 |

**两个不同口径的数放在同一列里用箭头连接，天然误导人以为「从 93 提升到 100 = 质量变好了」。** 实际上 v2 的 100 只是「12 项结构检查全过」，它没有经过独立审校，也没有事实断言核验。

08-26 的工作区日志第 11 行自己就写过这个观察：
> 「v1 机械审核亦100分，但4-AI差额分析仍发现语义级可优化点 → 印证"脚本过≠内容无优化空间"」

**结论**：得分问题有三层，从表到里是
1. **表层**：仪表盘数字与 review.json 不符
2. **中层**：表头降级，v1 分无处可填
3. **深层**：v1/v2 本就不同口径，列设计隐含了错误的可比性假设

### 2.4 修法与判断

| 优先级 | 建议 | 说明 |
|---|---|---|
| 🔴 | **恢复 6 列表头**，并在表头注明口径 | `\| 日期 \| 话题 \| AI数 \| 新FP \| v1分(R)→v2分(S) \| 状态 \|`，R=Reviewer 综合分、S=脚本分 |
| 🔴 | 把 7 次历史数据按 review.json 回填修正 | 08-24=96、08-26=96、08-27=92、08-28=93、08-31=93 |
| 🟡 | **考虑给 v2 也加一道独立审校**（或至少标注「未独立审校」） | 否则 v2 的 100 分含金量存疑；但会增加一次 spawn 成本与 3 到 5 分钟耗时 |
| 🟡 | 在 L2 SOP 中禁止修改质量仪表盘表头 | 增加一句「表头结构固定，不得增删列」 |

关于第 3 条我犹豫过：给 v2 加独立审校会让每天多一次 spawn。但考虑到 **L2 优化版才是最终对外发布的版本**（初稿反而不发布），而它恰恰是唯一没有独立视角校验的版本——这个风险值得花那 3 到 5 分钟。**建议做，但可以做成可配置开关先观察一周。**

**07-24 移除时没有回收编号**，于是 FP-01 到 FP-66 之间留下一个空洞。条数 = 65，编号上界 = 66。

### 3.2 「66」这个数字的确切来源

`reviewer_prompt.md` 第 43 行：

> 扫描 **FP-01 到 66 全部规则**（数量以文件实际内容为准，动态扫描编号，不要写死上限）。

**这句话自相矛盾**：前半句写死 66，后半句说别写死。而执行者（AI）只会执行前半句——后半句的免责声明在 prompt 里等于不存在。

同文件第 122 行的版本声明又把错误固化了一遍：
> *Version: v2.0 | 2026-08-20 | ... CHECKLIST 94 项/FP 66 条 ...*

（顺带一提，CHECKLIST 现在已是 100 项，这个 94 也过期了。）

### 3.3 讽刺的地方

08-20 那次「复活 reviewer_prompt.md」的工作，在日志第 89 行明确记着：

> | reviewer_prompt.md 未纳入 git 推送 | ⚠️→✅ 已补：config.json git_add_files + l3_publish.py files_to_copy |

**文件同步做得很到位，但这个文件从来没被调用过**——见第 5 节。所以一个「同步得很勤快」的文件，把错误数字传播到了全链路。

### 3.4 判断

- 编号空洞是**休眠归档机制的正常代价**，FP-58 归档是正确操作，不该为凑整数去回收编号（回收会让历史引用全部错位）。
- 真正该修的是**表述方式**：把「FP-01 到 66 全部规则」改成「扫描文件内全部 FP 条目（当前 65 条，编号不连续属正常）」，并删掉后半句自相矛盾的免责声明。
- 更彻底的做法：在 FORBIDDEN.md 头部用脚本自动注入 `<!-- FP_COUNT: 65 -->`，各处方读取该标记而非硬编码。

## 4. 字数：规则写了，代码没实现

### 4.1 SOP 的规定很清楚

`daily-why-writer/SKILL.md`：
- 第 116 行：**字数：300-600 中文字符（>600→P1）**
- 第 146 行：P1 重要 = AI味/连接词≥3、**字数>600** 等

`reviewer_prompt.md` 第 62 行：P1 重要 = **字数>600**、类比失准、绝对化 等

**三处都写了「>600 → P1」。**

### 4.2 但 validate_article.py 里这条检查是空的

```python
# 字数
WC_MIN = _r("word_count.min", 300)
WC_MAX = _r("word_count.max", 600)
WC_P1_THRESHOLD = _r("word_count.p1_threshold", 600)
```

常量定义了，但 grep 全文，`600` 只在这两行**定义处**出现，**没有任何调用点**。

**这是一条「定义了但从未接线」的规则。** 常量躺在那里，看起来很专业，实际不参与任何判定。

### 4.3 两道防线同时落空

| 防线 | 应该做什么 | 实际 |
|---|---|---|
| 脚本层 | `char_count > 600` → P1 | 常量存在，无调用 → **不拦** |
| 人工层 | Reviewer 按 reviewer_prompt 检查字数>600 | reviewer_prompt **从不被加载**（第 5 节）→ **不查** |

结果：08-31 通俗版 654 汉字（全文口径）超限时，两个脚本都判 PASS。

### 4.4 两个口径的差值来源已实测确认

我一开始以为是两套算法，实测后推翻了：

```python
# format_checker.py:60  ← validate_article.py 用的
len(re.findall(r"[\u4e00-\u9fff]", text))
# l3_publish.py:285
len(re.findall(r"[\u4e00-\u9fff]", text))
```

**算法完全相同。** 差在输入：

```
全文汉字数(l3口径)      : 452
剥离 markdown 后(validate): 377
差值                      : 75  ← 恰好等于结尾表格的汉字数
```

`validate_article.py` 先跑 `strip_markdown()`，该函数用 `re.sub(r"\|.+\|", "", text)` **整行删掉表格**，再统计。所以：

- **validate 口径 = 正文汉字数（不含结尾表格）**
- **l3 口径 = 全文汉字数（含结尾表格）**
- 差值恒等于表格字数（约 75 字，随话题略有浮动）

### 4.5 判断

**不建议简单改成全文口径。** 理由：结尾表格是**固定模板**（话题/分类/核心机制/冷知识反转四行），每篇都有、不随内容增减，把它计入「字数」会让所有文章的字数凭空 +75，压缩真正的正文空间。

**建议：**

1. **口径定死为 validate 口径**，并在 SOP 里写明定义：「字数 = 剥离 Markdown 标记与结尾风格表格后的正文汉字数」。这样通俗版 583 合规。
2. **给 validate_article.py 补上缺失的调用**——这是本次追查里最该修的一行代码：
   ```python
   if char_count > WC_MAX:
       result.p1.append(f"字数 {char_count} 超过上限 {WC_MAX}")
   ```
3. **废除第三个口径**：automation memory 里自记的「汉字 654」属于手工计数，与两个脚本都不同，应停止记录，统一引用 `validate_article.py` 的输出。
4. 若 Master 需要特批超限（如本次通俗版），应有**显式的特批标记**写在文章或日志里，而不是靠「脚本没拦住」这种隐性豁免。

## 5. Reviewer 严重性判定偏低：标准存在，但从未传给 Reviewer

### 5.1 分级标准其实写得很清楚

`reviewer_prompt.md` 第 61-63 行：

```
- **P0 致命**：事实错误、逻辑矛盾、结构缺失、Q用h3、分隔线>2
- **P1 重要**：AI味/连接词≥3、字数>600、类比失准、绝对化 等
- **P2 一般**：措辞微调、风格表格不完整
```

**「绝对化」明确归 P1。**

而 08-31 的 Q3「单靠这层气垫其实炒不熟菜」——四家 AI（ds/IMA/千问/豆包）一致判定为绝对化、应 P0 修正——Reviewer 只给了 P2。

### 5.2 但这份标准，Reviewer 从头到尾没见过

我查了当前 automation prompt（数据库里的 5004 字符全文）：

```
含 reviewer_prompt : False
含 绝对化          : False
含 P1 重要         : False
含 字数>600        : False
含 CHECKLIST       : True
含 FORBIDDEN       : True
```

**自动化 prompt 让 Reviewer 加载 CHECKLIST 和 FORBIDDEN，但从不加载 reviewer_prompt.md。**

所以 Reviewer 拿到的是：
- ✅ 跑脚本
- ✅ 读 CHECKLIST（100 条自检项）
- ✅ 读 FORBIDDEN（65 条禁令）
- ✅ 事实核验 → 错就标 P0
- ✅ 结构验证 → 缺就标 P0
- ❌ **P0/P1/P2 到底怎么分级 → 没有标准，自己看着办**

于是它把「绝对化」当成了「措辞微调」，归入 P2。

### 5.3 副作用：扣分尺度完全不一致

| 日期 | P2 数 | score | 每个 P2 平均扣 |
|---|---|---|---|
| 08-21 | 4 | 100 | 0 |
| 08-24 | 5 | 96 | 0.8 |
| 08-26 | 2 | 96 | 2.0 |
| 08-28 | 4 | 93 | 1.75 |
| 08-31 | 2 | 93 | 3.5 |

08-21 有 4 个 P2 却给 100 分，08-31 只有 2 个 P2 却给 93 分。**没有统一扣分标准，每天的 Reviewer 各自发挥。** 这让跨日的质量趋势对比失去意义——而仪表盘恰恰在拿这些分做趋势。

### 5.4 判断

这是本次追查中**修复性价比最高**的一项：

- 不需要写新标准，标准已经写好了（reviewer_prompt.md 第 61-63 行）
- 只需要在 `generate_prompt.py` 的 Reviewer 任务步骤里，加一行 `Read 加载 reviewer_prompt.md`
- 同时把该文件的过期数字修掉（94 项 → 100 项、FP 66 → 当前 65 条）

**一句话**：08-20 花了力气把 reviewer_prompt.md 复活并纳入 git 同步，却漏了最关键的一步——**让它被调用**。文件同步得再勤快，不进执行链就是死文件。

## 6. 其余小问题的成因

### 6.1 IMA 备份历史表：正则要求表格，实际是纯文本 → 从未生效过

`l3_publish.py` 第 514 行：

```python
def _append_ima_history(note_id, version, date_str):
    pattern = r"(## IMA 备份历史[^\n]*\n\|.*\|.*\|.*\|.*\|(?:\n\|.*\|.*\|.*\|.*\|)*)"
```

正则要求匹配**至少一行 4 列管道表格**。而 MEMORY.md 实际内容是：

```
## IMA 备份历史（最近5）
v6.6(08-26) v6.5(08-25) v6.4(08-24) v6.3(08-21) v2026.0827(...)
```

**一行纯文本，没有表格。** 正则匹配失败 → 静默 `return`，不写任何东西，也不告警。

**这不是「今天失效」，是这个函数从被写下那天起就没成功过一次。** 也解释了为什么备份历史一直是手写的那种紧凑格式——因为从来就没有自动追加过。

（note_id 本身是可信的：它由第 565 行 `re.search(r"note_id[:\s]+(\d+)", output)` 从 ima_archive.py 的 stdout 解析，并成功写进了 automation memory.md，只是没进 MEMORY.md。）

**修法**：改成「在 `## IMA 备份历史` 标题后的下一行插入」，不依赖表格格式；并加写入后回读校验，失败则 P1 告警（不能静默）。

### 6.2 commit message：硬编码模板

`l3_publish.py` 第 729 行：

```python
commit_msg = f"daily-why {date_str}: {topic} + 投喂优化 + 规则更新"
```

只有 `date_str` 和 `topic` 是变量，**「投喂优化 + 规则更新」写死**。所以当天只提交了 1 个 `topic_candidates.json`、且没有任何规则变更时，消息依然宣称「规则更新」。

**修法**：由实际 `git diff --name-only` 反推描述。例如检测到 references/* 变更才写「规则更新」，检测到 articles/* 才写文章名。

### 6.3 review.json 时间戳指向未来

`review_timestamp: "2026-08-31T15:45:00+08:00"`，文件实际写入 09:53:28，审计时系统时间 12:00。

**成因**：子 agent 没有取系统时间，凭自己（错误的）时钟概念生成。这不是脚本 bug，是 prompt 没约束。

**修法**：在 Reviewer 任务步骤里明确要求「用 `date` 命令取系统时间写入 `review_timestamp`，禁止自行推断」。

### 6.4 automation_runs.status 恒为 PENDING_REVIEW

数据库 15 条记录全是 PENDING_REVIEW，包括 `result_success=0` 的失败记录（08-26/08-27 的 automation-4「Automation prompt stopped before completion」）。

**成因**：平台侧字段未随执行结束更新，本地无法修。

**应对**：在审计 SOP 里写明「status 字段不可用于判定成败，一律用 `result_success`」。

### 6.5 run output 重复渲染 + 4000 字符截断

`runs_json[0].output` 长度**恰好 4000**，且同一段话出现两次（08-28 同样存在，且 08-27 的 Reviewer 输出里还有重复的英文自言自语）。

**成因**：平台侧行为，本地无源码可查。

**影响**：阶段 3/4 的执行记录在数据库侧丢失，只能靠文件 mtime 反推。本次追查的时间线就是这么重建的。

**应对**：在审计 SOP 中固化为「output 不可全信，须与文件 mtime 交叉验证」。

### 我对这套系统的整体判断

追查完这 7 类问题，有一个共性值得说：

**这些问题几乎都不是「写错了」，而是「写好了但没接上」。**

- 字数上限：常量定义了，没接线
- 审校分级：标准写好了，没加载
- IMA 历史表：函数写好了，正则匹配不到
- reviewer_prompt：文件复活了、同步了，没调用
- Phase 顺序：原本自洽，补同步清单时没回头看数据流

**规则和代码都不少，缺的是「 wiring 检查」——一个东西被定义/创建/同步之后，有没有真的进入执行链。**

所以除了上面 15 条具体改进，我建议补一条**通用的工程约束**：

> 任何新增的规则常量、标准文件、同步清单项，在合入时必须回答一个问题：**谁会读它？在哪个执行步骤读？** 答不上来的，就是下一个「死文件 / 空常量」。

这条约束如果落地，上面 1、2、5、6 这四条（都是高优先级）根本不会出现。
