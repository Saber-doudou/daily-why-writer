# 记忆管理外部经验调研报告

日期：2026-09-07
调研人：由 Master 指派，针对「MEMORY.md 反复超限截断」问题搜集 GitHub 与社区经验，并对照橙皮书内部范式
结论先行：**外部经验高度验证此前方案 C 的方向（索引化分片 + 机械门禁 + 切断自动写入），另新增 3 个可直接落地的增量动作。**

## 一、外部经验核心要点（5 个来源）

### 1. zackbot：三条自强制纪律（实测 211 行压到 62 行，减 70% 零信息损失）

来源：https://zackbot.ai/blog/stop-letting-your-ai-memory-files-bloat-fix-this-before-it-costs-you

1. **行数硬上限**（80 行）：没有上限就没有压缩触发点，每次写都应成为一次潜在的压缩时机
2. **compact-on-write**：编辑任何记忆文件前先重读，新信息**合并进现有章节，禁止盲目追加**，同时删除已被取代的内容
3. **staleness sweep**：读到记忆文件时发现过期/冗余内容，顺手清理，不需要专门发起

配套建议：按主题组织而非按时间；用紧凑格式（表格、行内列表）；主文件只做索引，细节放主题文件。

### 2. claw-stack：最对症的一篇（六周 700 行的血泪 + 三个反思）

来源：https://claw-stack.com/en/blog/persistent-memory-system

- 现象：不设限的 MEMORY.md 六周涨到 700 行，**session 启动吃掉大部分 context 预算**，模型边综合几百行简报边干活，明显变笨
- 修法：写入方不再直接追加 MEMORY.md，而是写 per-topic 文件，MEMORY.md 只放**一行指针**（「current status 见 projects/claw-stack.md」）；并强制**字节级上限**
- 定位重构：**MEMORY.md 不是「agent 知道的一切的摘要」，而是 session briefing（会话简报）——启动所需的最小上下文，其余一律按需取**
- 三个「如果重来」：
  1. 从第一天就设小上限（他们浪费了几周清理本可避免的膨胀）
  2. **尽早分离 episodic（周二发生了什么）与 semantic（系统架构是什么）**，两种记忆检索策略不同
  3. **先建审计工具**：维护记忆系统最难的不是索引和检索，而是「知道记忆什么时候错了」——审计视图应该是第一个工具，他们建晚了

### 3. fazm.ai：倒 U 曲线与 30 天引用追踪（反直觉数据）

来源：https://fazm.ai/blog/contextual-relevance-vs-over-reliance-memory

- **记忆量与 agent 表现是倒 U 曲线**： Helpful 到某一点后主动有害。500 行时 agent 开始把 A 项目的建议错用到 B 项目
- **30 天实测**：约 40% 的记忆条目从未被引用；另有 30% 被引用但导致更差结果（语境已变）；**只有 30% 持续有效**
- 建议：200 行以内；每周 review；60 天前的条目默认删；条目要「引导判断」而非「命令行为」
- 过度依赖的征兆：agent 背诵记忆文件而不是推理当前任务；旧 workaround 被用在没有该 bug 的场景

### 4. segmentfault（中文 OpenClaw 实践）：只存结论不存过程

来源：https://segmentfault.com/a/1190000047666900

- MEMORY.md 越短越好，recall 都要扫它；**只存结论，日志流水放 memory/YYYY-MM-DD.md 按需读**
- search 加 get（按行号取片段）组合，token 降 70% 至 80%
- 心跳文件保持空；重活扔 subagent（干净 context，主会话只收摘要）

### 5. dev.to（kiravaughn）：分层上下文与激进压缩

来源：https://dev.to/kiravaughn/optimizing-ai-agent-memory-tiered-context-and-aggressive-compaction-4bei

- 工作区自动加载文件压到合计约 7KB：只留核心规则、工具说明、身份、用户偏好
- **长记忆 MEMORY.md 不自动加载**，靠语义搜索按需取；明确写进规则「search before answering」
- 分层压缩配置：safeguard 模式（分段摘要不粗暴截断）+ 提前触发阈值

## 二、GitHub 记忆层生态速览（是否需要引入工具）

来源：https://niteagent.com/blog/ai-agent-memory-comparison-2026/ 、https://alignify.co/zh/blog/agent-memory 、https://codex.danielvaughan.com/2026/05/29/agent-memory-persistence-patterns-long-term-memory-stores-rag-beyond-context-compaction

| 方案 | 形态 | 适合谁 | 对本项目的适配度 |
|---|---|---|---|
| Mem0（约 48K 至 59K star） | 托管 API + OSS，抽取、去重、检索管线 | 快速接入任意框架的平台团队 | 低：为多用户多会话设计，单人流水线用不上，且图特性在 Pro 档（249 美元/月） |
| Zep / Graphiti | 时序知识图谱（事实带有效期） | 合规、金融等「去年信 X 今年信 Y」场景 | 低：需要图数据库运维，收益对不上 |
| Letta（原 MemGPT） | OS 式三层记忆（core/archival/recall），agent 自管分页 | 长运行自治 agent | 中：理念与方案 C 同构，但引入整个运行时过重 |
| claude-mem / agentmemory | IDE 侧会话记忆插件 | Claude Code / Cursor 用户 | 低：绑定别的 IDE harness |
| BasicMemory | 纯 Markdown 文件 + MCP 搜索 | 想要记忆可 git push 的开发者 | 高（理念同构）：**但 WorkBuddy 已有原生 memory 目录 + 注入机制，无需外挂** |
| **Markdown 文件 + 语义搜索** | 纯平文件 | 单人、脚本化流水线 | **alignify 原文结论：单人先用 MEMORY.md 模式，确有审计 API 需求再迁移** |

**选型结论：不引入外部记忆层。** 本项目是单人、单自动化、脚本化的 Markdown 体系，痛点是「注入配额管理」而不是「检索质量」，方案 C（分片 + 门禁 + 断源）零依赖即可解决。Mem0 类工具解决的「写时抽取去重」倒是可以借鉴其**写入时合并**思想（即 compact-on-write）。

## 四、差距分析：哪些已做对、哪些缺

### 已做对的（不用动）

| 实践 | 对应外部经验 |
|---|---|
| 每日日志按日期分文件（101 个，不注入） | claw-stack 的 episodic/semantic 分离、segmentfault 的「流水放 daily 文件」 |
| 压缩前全量快照备份（09-02、09-07） | EXP-012 跑前快照、EXP-015 快照回滚 |
| 字符数（而非行数）作为门禁单位 | claw-stack「字节限制比行数限制更可靠」 |
| check_memory_size.py 已建并反向验证 | claw-stack「先建审计工具」、EXP-004 约束优于指令 |
| automation memory.md 倒序 + head -150 防护 | dev.to 的按需读取 |

### 缺的（外部经验补齐）

| 缺口 | 外部依据 | 严重度 |
|---|---|---|
| 写入无合并纪律：AI 盲目追加不重读 | zackbot compact-on-write | 高 |
| 条目无生命周期：没有「最后被引用」概念，缺陷台账 1747 字符常驻注入区 | EXP-012 Curator、fazm 40% 从未引用 | 高 |
| MEMORY.md 混装三种性质内容（常驻规则/当前状态/历史档案） | claw-stack session briefing 定位 | 高 |
| 无引用审计：不知道哪些条目真的被用过 | claw-stack「audit tooling 先行」 | 中 |
| 无 staleness sweep 习惯 | zackbot | 中 |

## 五、合并进方案 C 的执行清单（v2）

在原方案 C（分片 + 门禁 + 切断 l3_publish 自动写入）基础上，新增 4 项：

1. **写入纪律写进 MEMORY.md 头部**（3 行，成本约 120 字符）：
   - 写前必重读，合并进现有章节，禁止盲目追加
   - 每行自问「删掉会导致犯错吗」（EXP-003 判据）
   - 读到过期内容顺手清理
   - 注意：按 EXP-004，这三行是行为软约束，真正的保障仍是 check_memory_size.py 机械门禁
2. **条目生命周期标记**（借鉴 EXP-012 Curator）：每条记忆带「最后引用」日期，审计时把 30 天未引用的降级下沉、90 天的归档，**永不删除**。首轮实施时缺陷台账 #6（1086 字符）、已修复 #7（661 字符）直接按此规则下沉
3. **引用审计**（claw-stack 反思第 3 条）：审计 SOP（daily-why-health-audit）加一步：抽查 3 条记忆条目本周是否被实际引用，连续两周未被引用的进入下沉候选
4. **automation memory.md 同样治理**：899 行且每天 +15 行，超出 1000 行自动归档上半年（可挂进 l3_publish 或审计流程）

预期效果（算术账）：
- MEMORY.md 6568 → 约 3600 字符（切 #6#7#9#10 四个档案区，共 2933 字符，索引行补偿约 300）
- 若 #5 A 方案落地细节（675）也下沉，降至约 2900，回到限额内
- 每日新增写入从约 1235 降至约 400 至 600（缺陷只在解决时入索引一句话，细节进分片）
