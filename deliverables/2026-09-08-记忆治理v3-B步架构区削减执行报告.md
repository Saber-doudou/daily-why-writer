## 一、决策说明：为什么选 B（先砍架构区）

Master 说「就是个先后顺序」，方向上没错，但两件事的**风险量级和依赖关系不同**，所以顺序不是随意的：

| 维度 | B（先砍架构区） | A（先做门禁前置 L1） |
|---|---|---|
| 改动对象 | 本地 Markdown + 自家脚本 | 自动化 prompt + **写库** |
| 失败代价 | 快照回滚，秒级 | 09-01 有写库损坏先例，排查成本高 |
| 与报警的关系 | 消除报警源 | 制造报警源 |
| 前置依赖 | 无 | **依赖内容先干净** |

关键在第三行。门禁一旦前置到 L1，每天都会跑一次分区检查；如果架构区带着 683/550 的红点上线，那么从第一天起日志里就有一个**没人打算处理的告警**。这正是 EXP-014「可观测性即诚实性」要防的反面：报警说了，但等于没说。

所以先洗干净，再开报警。这一步低风险、可逆、且是 A 的前置条件。

## 四、三处机制改进（不只是删字）

### 1. 分片索引配额改为动态（38/条 + 44）

原配额写死 300。但分片索引的行数等于分片数，是**刚性增长**的，每新增一个分片就会告警一次，逼着人去改配额数字来适配内容，这是典型的「改规则迁就现状」，违反 EXP-004。

改为 `38 × 条目数 + 44`，新增分片时配额自动跟着走，无需人工干预。

### 2. 用户级记忆改为「仅提示，不阻塞」

用户级 MEMORY.md 当前 5163/4000（1.29x）超限，但 Master 已明确划定**不归本项目管理**。若计入退出码，门禁前置到 L1 后会每天阻塞在一个已知且不会被处理的告警上，结果是告警疲劳，真告警也被一并忽略。

处理方式：照常打印保持可见，但不计入退出码。哪天要接手，从 `NON_BLOCKING` 集合删掉即可。

### 3. 零损失校验转正为通用工具

临时脚本会变成死文件，但零损失校验后续每次下沉都要用（第 1 步四层归位、衰减淘汰都会删内容）。转正为 `scripts/verify_memory_migration.py`，且**不依赖手写清单**：

- 从快照与当前的差异中自动提取被删行的关键 token（反引号、标识符、数字、日期、AI 专名）
- 到 `topics/` 全目录 + `scripts/config.json` 检索
- 支持简写记法展开：`dailywhy学习(总结)/投喂` 自动展开为 `dailywhy学习` / `dailywhy学习总结` / `投喂`

相比手写清单的好处是**不会漏列**：没想到的 token 也会被提取。
