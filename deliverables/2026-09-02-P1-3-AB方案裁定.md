# P1-3 `--skip-match` 设计残留 — A/B 方案裁定

> 状态：**【2026-09-02 18:44 已裁定并实施 方案A · v3.8】** — 去 SOP 模板 `--skip-match` + 匹配结果纳 checksum 保护区，`--skip-match` 保留手动逃生阀；B 未采用，若 A 误拦截可回退

## 一、溯源结论（已查实，非新 bug）

- `--skip-match` 自 commit **fd1dedb（2026-06-22，v3.0 初版）** 起写死进 `daily-why-publish/SKILL.md` 模板第125行。即 v3.0 第一天执行模板就是 `l3_publish.py [日期] --skip-match --force`。
- 08-31 v3.6 引入 `render_report()` 时，把"语义验证表"留在 checksum 之后的 **AI 补充区**（不受保护），承接并合理化了这个一直被跳过的状态。
- 脚本侧 `--skip-match` 是可选开关（`action="store_true"` 默认 False = 默认跑 Phase 1），但**模板永久传 True**，故 Phase 1 实际从未运行。
- 性质：**设计残留，非后来事故性跳过的 bug**。

## 二、本质

L3 Phase 1（优化版是否匹配自动化产出的「匹配度检查」）**从未真正由脚本执行**。每次发布靠"人工看报告 + AI 在补充区补一句验证"代偿，而非代码强制门控。这与 08-31 防篡改修复的初衷（保护 render_report 渲染区）相悖——保护罩没盖到被跳过的 Phase 1 验证。

## 三、方案 A：恢复脚本验证（让 Phase 1 真正生效）

**改动**：
1. publish SKILL.md 模板第125行：去掉 `--skip-match`
2. l3_publish.py Phase 1 匹配逻辑恢复运行
3. 把匹配结果表从"AI 补充区"搬进 render_report() 的 **checksum 保护渲染区**

**影响**：
- ✅ 机制保证的真实门控：每次发布前脚本强制校验"优化版 ↔ 自动化产出"匹配，不匹配则拦截/告警；结果受 checksum 保护，不可被 AI 手写篡改
- ⚠️ 代价：Phase 1 匹配逻辑须健全（误报率低）。若匹配算法本身有缺陷，会**阻塞正常发布**，需人工放行
- 🔧 自动化：不变 L3 手动触发本质，仅 L3 内部多一道自动门；自动化仍只覆盖 L1

## 四、方案 B：删 Phase 1 + 参数 + AI 补充区依赖（诚实化）

**改动**：
1. publish SKILL.md 删 `--skip-match` 参数定义，明确"本流程不做脚本匹配验证"
2. l3_publish.py 删 Phase 1 步骤、删 render_report() 对 AI 补充区语义验证表的依赖
3. 文档诚实标注：匹配正确性依赖 L2 人工聚合 + L3 人工看报告

**影响**：
- ✅ 消除"看起来在验证、其实没验证"的假象，流程诚实简洁，审计无歧义
- ⚠️ 代价：彻底失去这道内部门控，匹配一致性**纯靠人工**，无代码兜底
- 🔧 自动化：同样不变 L2/L3 手动本质；实际行为变化很小（门本来就没开），只是从"假装开着（被 --skip-match 关了）"变为"承认没这门"

## 五、核心区别（一句话）

- **A = 把门真正修好并打开**（恢复代码强制校验 + checksum 保护），代价是要保证门逻辑对，否则会误拦截正常发布
- **B = 承认没有这门、把假门拆了**（诚实化），代价是匹配验证纯靠人工、无代码兜底
