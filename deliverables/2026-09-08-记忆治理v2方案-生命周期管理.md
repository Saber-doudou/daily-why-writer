> 范围：**仅工作空间级记忆**（`.workbuddy/memory/`）。用户级 `~/.workbuddy/MEMORY.md` 按 Master 明确指示**不在本方案范围**，不再提及。

## 一、先说结论：昨天方案 C 没做错，但只做了三分之一

昨天（daily-why）和 history 的改造，本质上都是**同一套动作**：快照 → 分片下沉 → 索引化 → 断源 → 门禁。

这套动作解决的是**存量**。三个项目的实测结果放在一起看，问题就暴露得非常清楚了：

| 项目 | 改造前 | 分片后 | 现在 | 回涨 |
|---|---|---|---|---|
| daily-why | 6568 | 2644 | **2985**（0.99x） | +341（1 天） |
| **history-today** | 7416 | **1840** | **3468（超限 1.16x）** | **+1628（16 小时，+88%）** |

**history 是最有说服力的证据**：09-07 20:00 分片完是 1840 字符（留 1160 余量），门禁反向验证也做了（注入 padding 正确拦截，EXP-014 合规）——**流程上无懈可击**。但 16 小时后我实测是 **3468 字符，又超限了**。

分片动作本身是成功的，**失败在分片之后**。

## 二、history 改造的可借鉴点（3 个）与失败教训（1 个，关键）

### 可借鉴

**1. 分片映射表 + 逐区段三档决策**
history 方案第四节对每个区段明确标注「下沉 / 精简保留 / 完整保留（不可下沉）」并写理由。比我们的粗放分片精细，且「不可下沉区」这个概念值得保留——它对应"每会话必须见"的内容。

**2. 门禁集成在日常检查里（sync_check），而不是只在发布流程里** ⭐ 最重要
history 把记忆门禁接进 `sync_check` ⑧，**每次 L1 运行都查**。
而 daily-why 的 `check_memory_size.py` 只接在 **L3 Phase 0**——L3 是**手动触发**的。这意味着：**每天真正产生增长的 L1 环节，完全无人监管。** 这是我们必须抄过来的。

**3. 双路径统一**
消除 automation memory 的 A/B 双写分裂。daily-why 无此问题，但"权威路径唯一性断言"这个做法值得学（防止再次分裂）。

### 失败教训 ⭐⭐⭐

**"精简保留"是最大的漏洞。**

history 分片后保留了「铁律 + 执行规范 + 发布规范 + 运维速记」四个区，结果 16 小时内这些区被持续追加，1840 涨到 3468。

看它现在的实际内容就明白了——这些是"精简"后的行：

- 执行规范第 33 行（版本号规则）：**250+ 字符**，把「逢十进位 / major 可超 9 / 9.8.9+1=9.9.0 / v10+ 纪元 / sync_check ③ 同口径」全塞进一行
- 第 35 行（选题索引）：200+ 字符，带历史脉络说明
- 第 21 行（逢十进位）：150+ 字符

**所谓"精简"，实际是把细节压缩成超长单行，字符数几乎没降。** 而 AI 看到"这是保留区"就认为"这里可以写"，于是持续追加。

**daily-why 完全同构**：#3 铁律区 1271 字符占 42.6%，是唯一增量区，被完整保留且无任何写入限制。我昨天审计时加 4 条就顶穿上限——和 history 是同一个机制、同一个结果。

## 三、外部经验：我们缺的那一环是「遗忘」

### 3.1 核心发现（5 个来源）

| 来源 | 关键结论 | 对我们的意义 |
|---|---|---|
| **AWS AgentCore 生命周期策略** | 记忆分三类：Episodic（事件，TTL 90 天优先过期）/ Semantic（事实，6-12 月）/ **Procedural（程序性经验，最长保留、最高修剪门槛）**。但明确说：Procedural 也 **"should check these for validity as your procedures evolve"** | **铁律 = Procedural 型**。不是"永不淘汰"，而是"高门槛 + 有效性复审"——这解开了我们"铁律不能删 vs 铁律只增不减"的死结 |
| **happyin.space 遗忘策略** | 衰减评分公式：`0.3×recency + 0.3×access_freq + 0.2×freshness + 0.2×type_weight`；**Refresh-on-Read**（被读取则提升分数并重置计时器）；状态机「活跃→低频→归档→过期」且**可回升** | 可直接改造成我们的铁律衰减评分；"被引用才算有用"是可量化的 |
| **Context Engineering（Bob）** | Progressive Disclosure 实证：**750 token 索引替代 11,000 token 单体文件，缩减 93% 且零信息损失**；反模式 Token Sprawl 的修法是「审计 auto-include，若文件在最近 50 个会话未被引用，它不值这个 token 成本」 | 索引化的收益有量化背书；"未引用即降级"有了明确标准 |
| **State of Context Engineering 2026（Anthropic Agent Skills 三层）** | Discovery（只读 name+description，约 80 token）→ Activation（相关才加载全文 275-8000 token）→ Execution（脚本/参考材料执行时才加载）。**触发率 >30% 的规则说明关键词过宽** | 铁律应按「触发场景 → 按需加载」组织；**30% 反过来用：只有触发率 >30% 的才配常驻全文** |
| **zylos.ai 综述 + MEMTIER 论文** | **flat memory 系统在 72 小时内工具执行成功率下降 14 个百分点**；200K 窗口在约 130K 就出现可测退化；无遗忘策略"guarantees budget overrun" | 给 Master 的硬数据：不治理的代价是可测量的能力衰减，不只是"文件太大" |

### 3.2 一句话总结外部经验

> **"Infinite retention is an architectural bug, not a feature."**（无限保留是架构缺陷，不是特性）

我们和 history 都把记忆当成**只增不减的账本**，而业界共识是把它当成**有生命周期的生态系统**——该归档的归档、该降级降级、该合并的合并，且**归档 ≠ 删除**（先归档后移除，这与我们"分片零损失"的原则完全一致）。

## 四、更优方案：五道闸门

范式转换：**从「一次性排水」转向「流入控制 + 存量衰减」双管齐下。**

### 闸门 1｜写入准入（Write Admission）—— 治增量

**现状**：门禁是事后报警，warn 不阻断，AI 想写还是写。写入纪律是 102 字符的纯文本（又是一次 EXP-004：指令约束 ≠ 机制约束）。

**做法**：提供唯一写入口 `append_memory.py`（或对 Edit 加 pre-check），写入前强制声明：

```
新增 X 字符 → 削减来源：第 N 条（替换/下沉）→ 写入后总量 Y
```

无削减来源且将导致超限 → **拒绝写入并指出该削哪一区**。

**为什么有效**：把"写前重读、合并进现有章节"从建议变成机制。这是 EXP-004 的正解。

### 闸门 2｜分区配额（Section Quota）—— 治保留区膨胀（history 的致命伤）

**现状**：门禁只报总量 2985/3000，AI 无从下手——要么不动，要么乱删。

**做法**：给每个区设硬上限，超限直接点名：

| 区 | 建议上限 | 当前 | 性质 |
|---|---|---|---|
| #3 铁律（Procedural） | 700 | **1271** ⚠️ | 唯一增量区，重点管控 |
| #1 架构与自动化 | 550 | 684 | 基本稳定 |
| 分片索引 | 300 | 255 | 随分片数缓增 |
| #2 写作规范指针 | 200 | 186 | 稳定 |
| #4 IMA 约束 | 150 | 154 | 稳定（已断源） |
| 写入纪律 | 120 | 102 | 稳定 |
| **合计** | **2020** | **2985** | 留 980 缓冲给新写入 |

### 闸门 3｜单行长度闸（Line Width Gate）—— 治"压缩成超长单行"

**现状**：history 第 33 行 250 字符是典型——"精简"变成了把论证过程压进一行。

**做法**：
- 单行 > 120 字符 → 强制拆行或下沉到 `topics/`
- 一条铁律 = **1 行**，格式固定为「触发场景 → 动作 → 指针」，**不含论证过程和历史脉络**
- 论证过程放 `topics/iron_rules.md`（那里没有 3000 限制）

### 闸门 4｜衰减与淘汰（Decay & Eviction）—— 治"只增不减"⭐ 最关键，我们完全没有

**这是三份外部材料共同指向的核心机制，也是 daily-why 和 history 都缺的一环。**

**铁律元数据**（存在 `topics/iron_rules.md`，MEMORY.md 只留摘要行）：

```yaml
- id: EXP-004
  summary: 约束优于指令（改 prompt 须配机械校验）      # ≤30 字
  type: procedural                                    # 最高保留优先级
  trigger: "改 prompt / 加防复发机制"                  # 触发场景，供渐进式披露
  created: 2026-09-01
  last_accessed: 2026-09-08
  access_count: 12
```

**衰减评分**（改造自 AWS + happyin 公式）：

```python
score = 0.3*recency(30天半衰期) + 0.3*access_freq(min(n/10,1))
      + 0.2*freshness(7天半衰期) + 0.2*type_weight(procedural=1.0)
```

**处置规则**：

| 条件 | 处置 |
|---|---|
| score ≥ 0.6 **或** 触发率 > 30% | **常驻全文**（预计 15 条里只有 3 到 5 条够格） |
| 0.3 ≤ score < 0.6 | 降为**触发式索引行**（保留「触发场景 → 指针」一行） |
| score < 0.3 且 90 天未访问 | 下沉 `topics/`，MEMORY 删行 |
| **type = procedural** | **永不删除，只降级**（对应 AWS「最高修剪门槛」） |

**Refresh-on-Read 埋点**：脚本定期扫描 `deliverables/` 与 `.workbuddy/memory/*.md` 中铁律 ID 的出现次数，自动更新 `access_count` / `last_accessed`——**不用人工维护**。

**关键设计**：这解决了"铁律不能删"与"铁律只增不减"的矛盾——**不是删除，是降级**；且被引用多的会自动回升（状态机可双向）。

### 闸门 5｜渐进式披露（Progressive Disclosure）—— 治常驻区过载

借鉴 Anthropic Agent Skills 三层：

| 层 | 内容 | 加载时机 |
|---|---|---|
| L1 Discovery | 每条铁律 1 行：`触发场景 → 动作 → 指针`（约 45 字符） | **常驻** |
| L2 Activation | 命中触发场景时读 `topics/iron_rules.md` 对应条目全文 | 按需 |
| L3 Execution | 原始案例、论证过程、历史脉络 | 排障时 |

**估算**：5 条常驻全文（100 字）× 5 + 10 条索引行（45 字）× 10 = **约 950 字符**，比现在 1271 省 320，且**结构稳定，不再线性增长**。

**对冲风险**（我昨天的担心：降级后 AI 不知道要查）：把**触发场景写进索引行本身**——「凡改版本号 → 查 §7 版本号易腐」。索引行自带触发信号，比全文常驻弱，但比整块下沉强。这是 3000 字符约束下的最优解。

## 五、配套动作

### 5.1 门禁前置到 L1（抄 history）⭐ 必做

daily-why 的 `check_memory_size.py` 现在只接在 **L3 Phase 0**（手动触发），而增长 100% 发生在 L1（每天自动跑）——**等于给后门装了锁，前门敞开**。

做法：把体积检查加进 L1 自动化 prompt 阶段 3 之后，或作为 L1 post-run hook。history 集成在 sync_check 的做法直接抄。

### 5.2 周度棘轮（Weekly Ratchet）

建议每周五 L3 后跑一次：
1. 衰减评分输出「待降级 / 待下沉」清单
2. 审计常驻项：过去 20 个会话未被引用 → 降级（外部标准是 50 会话，我们体量小，用 20）
3. 合并重复经验（多条同类教训合成一条规则）

### 5.3 分片条目数控制

外部经验：**索引导航在约 500 条目时退化**。当前 topics/ 分片 8 个、条目远低于此，暂无需处理，但新增分片时应监控。

## 八、与昨天方案 C 的关系

**不是推翻，是补上缺的一环。**

方案 C（分片 + 索引 + 断源 + 门禁）解决了**存量**——这部分 yesterday 做得对，两个项目都验证有效（daily-why 断源后今天零增长就是铁证）。

v2 补的是**增量**和**衰减**：闸门 1/4 管流入与流出，闸门 2/3/5 管结构。两者是**正交**的，合起来才构成完整闭环：

```
存量（方案 C：分片下沉）  ──┐
增量（v2 闸门 1/2/3）      ──┼──→ 闭环
衰减（v2 闸门 4/5）        ──┘
```
