## 2026-11-10 复核口径（不是缺陷，是尺子）
- 说「DB 与交接件逐字节一致」前必须声明行尾口径：Python 文本模式默认 `newline=None` 会把 CRLF 归一成 LF；显式 `newline=''` 才读到原始字节。11-09 交接件按 Windows 文本模式重新生成带 127 个 `\r`，用后者读会显出 12175 vs 12302 的假漂移，归一后 sha 完全相同（f70e3dd8e0105738）。差 N 个字符先数是不是 N 个 `\r`，别急着报「内容被改」。
- 远端探活失败不等于仓库不一致。`delivery_check --remote` 里远端是附加项，失败只标「未校验」且仍 exit 0；GitHub 连接时通时断（5 次里 3 成 2 败）时，必须单独跑 `git ls-remote origin refs/heads/main` 并把 `$?` 紧跟在命令后捕获，禁止从管道下游取 RC。

## 2026-11-10 补丁传输：不要靠「事后 grep 补救」，要绕开源头
- 字节级补丁脚本经 shell heredoc 落地时，`:\n` 会被转成 `:/n`，本次是**第二次**踩同一个坑（11-09 已记过「落地后 grep :/n 再还原」）。这次预检直接报「锚点命中 0 次」把事故拦在写盘前，说明两遍执行设计有效。
- 但正确解法不是反复事后还原，而是**根本不走 shell**：把补丁器用文件写入（Write 工具）再 `python <file>` 执行，转义由 Python 解析器负责，一次通过零事故。同一类风险第二次出现时，应升级为「换工具链」而不是「加事后检查」。
